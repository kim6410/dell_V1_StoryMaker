# StoryMaker Beta 구조 결정 기록

마지막 갱신: 2026-07-24

## ADR-001 Beta는 V1과 완전히 분리한다

- 상태: 채택
- 결정: Beta는 별도 루트, DB, 작업 폴더, API, Worker, Supertonic, 렌더러를 사용합니다.
- 이유: 신규 개발 실패가 운영 V1에 영향을 주지 않도록 하기 위함입니다.
- 금지: V1 파일·DB 직접 수정, 공용 포트 7788 사용, V1 Worker·Queue 공유.

## ADR-002 Beta의 핵심 작업 단위는 beta_job_id다

- 상태: 채택
- 결정: 모든 입력, 결과, 로그, 자산은 `beta_job_id`로 묶습니다.
- 이유: 이전 작업 자산 혼입을 막고 보관함·복구·진단을 단순화합니다.
- 후속: 모든 비동기 결과는 현재 job_id 일치 여부를 검증해야 합니다.

## ADR-003 작업 결과 계약은 result.json을 중심으로 한다

- 상태: 채택, 개선 필요
- 결정: 콘텐츠와 자산 경로를 작업별 `result.json`에 기록합니다.
- 이유: 프런트·보관함·렌더러가 동일한 작업 결과를 읽을 수 있습니다.
- 위험: 여러 모듈의 전체 저장 충돌.
- 후속: 중앙 patch 함수, 잠금, revision을 도입합니다.

## ADR-004 Gemini는 브라우저 Worker 방식으로 연결한다

- 상태: 채택, 개선 필요
- 결정: 웹 Gemini와 Tampermonkey Worker를 사용해 SNS 콘텐츠와 썸네일 결과를 수신합니다.
- 이유: 별도 API 과금·키 의존성을 줄이고 현재 사용자 흐름을 활용합니다.
- 위험: 탭 상태, Worker 버전, 단일 Queue, 타임아웃.
- 후속: job별 Queue와 Worker lease를 도입합니다.

## ADR-005 MP4는 브라우저 렌더를 우선 고도화한다

- 상태: 채택
- 결정: WebCodecs·WASM·Mediabunny 계열 브라우저 렌더를 Beta 핵심 방향으로 삼습니다.
- 이유: 서버 자원 부담을 줄이고 사용자 PC 자원을 활용합니다.
- 원칙: 서버 FFmpeg 경로와 결과를 혼동하지 않고 렌더 모드를 명시합니다.

## ADR-006 V1 업체정보는 파일·DB가 아닌 읽기 전용 HTTP 경계로만 접근한다

- 상태: 조건부 채택
- 결정: 사용자가 로그인한 V1 프로필을 불러올 필요가 있을 때 승인된 HTTP API만 사용합니다.
- 이유: 사용자 편의성을 유지하면서 데이터 저장소를 분리합니다.
- 제한: V1 장애 시 Beta 자체 입력으로 계속 진행할 수 있어야 합니다.

## ADR-007 문서와 자동 검사로 AI 작업 인수인계를 표준화한다

- 상태: 채택
- 결정: `00_READ_FIRST`, `ACTIVE_WORK`, `CURRENT_STATE`, `KNOWN_ISSUES`, `ARCHITECTURE`, `WORK_LOGS`와 전·후 검사 스크립트를 사용합니다.
- 이유: 작업자가 바뀌어도 동일한 안전 규칙과 검증 절차를 적용하기 위함입니다.

## 새 결정 추가 규칙

구조·데이터 계약·포트·DB·렌더 방식처럼 장기 영향을 주는 선택은 `ADR-###`로 기록합니다. 결정 변경 시 기존 항목을 삭제하지 않고 상태와 대체 ADR을 표시합니다.
