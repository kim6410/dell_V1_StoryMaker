## 최초 증상

사용자 화면에서는 MP3 제작이 진행 중 상태에서 멈추거나 실패 화면으로 전환됐다.

그러나 실제 확인 결과 백엔드에서는 MP3가 정상 생성되고 파일 저장까지 완료된 경우가 있었다.

즉 실제 구조는 다음과 같았다.

```text
백엔드 MP3 생성 성공
↓
파일 저장 성공
↓
프론트엔드 완료 상태 반영 실패
↓
사용자는 제작 실패로 인식
```

핵심 문제는 MP3 엔진이 아니라 프론트엔드 상태 동기화와 실패 화면 UX였다.

## 문제의 심각성

백엔드에서 작업이 성공했더라도 프론트엔드가 완료 화면으로 넘어가지 못하면 사용자는 작업이 실패했다고 판단한다.

또한 실패 화면에서 다른 화면으로 이동할 수 있는 버튼이 없어 사용자가 화면에 갇히는 문제가 있었다.

따라서 이번 작업의 최우선 목표는 다음 두 가지였다.

1. 프론트엔드가 MP3 완료 상태를 다시 확인해 정상 화면으로 복구할 것
2. 실패하더라도 사용자가 다른 화면으로 이동할 수 있을 것

## 1차 조치

V1 프론트 보조 브리지에 다음 기능을 추가했다.

- 현재 작업 ID 기준 진행 상태 재조회
- MP3 완료 또는 MP3 URL 확인 시 완료 이벤트 전달
- 프론트가 계속 MP3 생성 중 상태라면 작업당 한 번만 화면 재동기화
- 실패 화면에서 탈출할 수 있는 버튼 제공

실패 화면에 추가한 이동 기능:

- 결과 다시 확인
- 내 보관함
- 새 작업
- 메인 화면

이제 실패 화면은 더 이상 사용자를 가두는 막다른 화면이 아니다.

## 재검증 중 발견한 추가 위험

초기 복구 코드는 3초마다 진행 상태를 확인하도록 구성했다.

그러나 이전 네트워크 요청이 끝나기 전에 다음 폴링이 시작될 수 있었다.

예를 들어 서버 응답이 느린 경우 다음과 같이 요청이 겹칠 수 있다.

```text
요청 A 실행 중
↓
3초 후 요청 B 시작
↓
요청 A와 B가 동시에 대기
↓
다시 3초 후 요청 C 시작
```

이 구조가 지속되면 다음 문제가 생길 수 있다.

- 네트워크 요청 누적
- Promise 누적
- 반복적인 DOM 검사
- 브라우저 메모리 사용 증가
- UI 버벅임 또는 멈춤처럼 보이는 현상

사용자가 가장 중요하게 요청한 것은 단순 탈출 버튼이 아니라 프론트엔드 자체가 멈추지 않는 것이었으므로 이 부분을 다시 검증했다.

## 최종 수정

진행 상태 확인 요청이 동시에 하나만 실행되도록 잠금 변수를 추가했다.

최종 동작은 다음과 같다.

```text
상태 확인 시작
↓
진행 중 플래그 설정
↓
이전 요청이 끝날 때까지 추가 요청 차단
↓
응답 처리 또는 오류 처리
↓
진행 중 플래그 해제
↓
다음 폴링 허용
```

이를 통해 느린 응답 상황에서도 요청이 겹쳐 쌓이지 않도록 했다.

## 무한 새로고침 방지

백엔드에서 MP3 완료를 감지했을 때 프론트 상태를 다시 읽기 위해 새로고침을 수행할 수 있다.

하지만 동일 작업에서 반복 새로고침이 발생하지 않도록 `sessionStorage`에 작업별 복구 여부를 저장했다.

## 이번 사고에서 얻은 교훈

### 1. 파일 생성 성공만으로 작업 성공이라 판단하면 안 된다

백엔드 로그와 파일이 정상이어도 사용자가 완료 화면을 보지 못하면 실제 서비스 관점에서는 실패다.

앞으로는 반드시 다음을 별도로 확인해야 한다.

- 백엔드 작업 완료
- 결과 파일 저장
- 프론트 완료 상태 반영
- 사용자 이동 가능 여부

### 2. 폴링은 반드시 중첩 방지 장치를 둔다

`setInterval` 안에서 비동기 요청을 실행할 때는 이전 요청 완료 여부를 확인하지 않으면 요청이 계속 겹칠 수 있다.

앞으로 모든 상태 폴링에는 다음 중 하나를 적용한다.

- in-flight 잠금 변수
- 요청 완료 후 다음 요청을 예약하는 `setTimeout` 방식
- `AbortController`를 이용한 이전 요청 취소

### 3. 실패 화면에는 항상 탈출 경로가 있어야 한다

실패 화면에서 사용자가 아무것도 할 수 없는 구조는 금지한다.

최소한 다음 중 두 개 이상을 제공한다.

- 재시도
- 결과 다시 확인
- 보관함 이동
- 새 작업
- 메인 화면

### 4. 자동 복구는 반드시 반복 방지 장치를 둔다

새로고침, 재시도, 상태 재조회 같은 자동 복구는 작업당 실행 횟수를 제한해야 한다.

### 5. 수정 범위를 먼저 고정한다

이번 작업처럼 운영 환경과 V1 환경이 함께 존재하는 경우 수정 전에 반드시 대상 경로와 수정 금지 경로를 문서로 고정한다.

## 다음 작업자가 반드시 확인할 체크리스트

1. 현재 브라우저에서 `Ctrl + Shift + R`로 최신 V1 프론트 코드를 적용한다.

3. 개발자 도구 Network에서 progress 요청이 동시에 여러 개 겹치지 않는지 확인한다.
4. MP3 완료 후 완료 화면 또는 결과 화면으로 정상 전환되는지 확인한다.
5. 고의로 오류 상황을 만들었을 때 실패 화면 탈출 버튼이 보이는지 확인한다.
6. 내 보관함에서 생성된 MP3가 정상 표시되고 재생되는지 확인한다.
7. 문제가 발생하더라도 운영 경로와 V2는 수정하지 않는다.

## 현재 결론

이번 문제는 MP3 생성 실패가 아니라 프론트엔드 완료 상태 반영 실패와 폴링 중첩 가능성이 결합된 문제였다.

최종적으로 V1 프론트에서 상태 확인 요청을 직렬화하고, MP3 완료 상태 재동기화와 실패 화면 탈출 경로를 추가했다.

앞으로는 백엔드 성공 여부뿐 아니라 사용자가 실제 완료 화면까지 도달하는지를 작업 완료 기준으로 삼는다.
