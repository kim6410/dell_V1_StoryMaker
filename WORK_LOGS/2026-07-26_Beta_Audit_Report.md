# StoryMaker Beta 종합 감사 보고서

이 보고서는 StoryMaker Beta 시스템의 현재 아키텍처, 성능, 저장 공간, 보안 등 모든 지표를 종합적으로 분석한 1차 감사 결과입니다. 현재 소스 코드(`beta_jobs.py`, `index.html` 등)와 설정, 데이터베이스 스키마를 훼손 없이 분석했습니다.

---

## 1. 최종 판정

- **현재 하루 500명·동시 접속 10명 운영 가능 여부**: **불가능 (즉시 서비스 금지 수준)**
- **조건부 가능 여부**: 크리티컬한 보안 및 동기 병목 문제를 해결한 뒤에만 운영 가능합니다.
- **즉시 서비스 금지 수준의 문제 여부**: API 보안 인증이 없고, 타인의 데이터에 임의 접근 가능한 IDOR가 뚫려 있으며, 이벤트루프를 막는 동기 FFmpeg 렌더링으로 10명 동시접속 시 CPU 및 API 서버가 마비되는 심각한 결함이 있습니다.

---

## 2. Critical 문제 (즉시 수정 필요)

### [CRITICAL-1] 전체 API 권한/인증 누락 (IDOR 취약점)
- **파일**: `StoryMaker_beta/app/beta_jobs.py`
- **함수**: `beta_create_job`, `beta_render_job`, `beta_get_job`, `beta_delete_job` 등 모든 라우터
- **정확한 원인**: 사용자 식별 및 권한 검증(Auth) 로직이 존재하지 않습니다.
- **재현 조건**: 누구나 브라우저 또는 cURL로 임의의 `beta_job_id`를 넣어 `DELETE /beta-api/jobs/{id}`를 호출하면 삭제됩니다.
- **사용자 영향**: 악의적 사용자가 작업을 무단으로 탈취/수정/삭제할 수 있습니다.
- **데이터 손실 가능성**: 매우 높음.
- **해결 방향**: 각 API에서 `cookie`나 `authorization` 헤더를 통해 사용자를 식별하고 DB에 `user_id` 칼럼을 추가해 본인 소유의 작업만 조작/조회 가능하게 해야 합니다.

### [CRITICAL-2] 서버 CPU를 점유하는 동기 FFmpeg 렌더링
- **파일**: `StoryMaker_beta/app/beta_jobs.py`
- **함수**: `beta_render_job`, `beta_make_video`
- **정확한 원인**: 요구사항(MP4 브라우저 렌더링)과 달리 백엔드에서 `subprocess.run`으로 FFmpeg를 실행합니다.
- **재현 조건**: 5~10명이 동시에 생성(Render) 요청.
- **사용자 영향**: 전체 API가 블로킹되거나 서버 리소스(CPU/RAM)가 포화되어 다운될 수 있습니다.
- **데이터 손실 가능성**: 렌더링 실패 및 Time out.
- **해결 방향**: FFmpeg 비디오 및 TTS 생성 로직을 프론트엔드 WASM/WebCodecs로 완전히 이관하거나, 서버에서 돌려야 한다면 비동기 작업 큐로 분리해야 합니다.

### [CRITICAL-3] 비동기 함수 내 블로킹 I/O
- **파일**: `StoryMaker_beta/app/beta_jobs.py`
- **함수**: `beta_create_job`
- **정확한 원인**: `async def` 안에서 `shutil.copyfileobj`를 사용해 업로드 파일을 복사합니다.
- **재현 조건**: 대용량 비디오/사진 업로드 시.
- **사용자 영향**: 파일이 디스크에 쓰이는 동안 Uvicorn 이벤트 루프가 정지되어 다른 모든 API 요청이 지연됩니다.
- **해결 방향**: 청크 단위로 `await upload.read()` 비동기 방식을 사용하거나 `def` 라우터로 변경해야 합니다.

## 3. High 문제

### [HIGH-1] SQLite WAL 모드 미활성화
- **파일**: `StoryMaker_beta/data/storymaker_beta.db`
- **정확한 원인**: PRAGMA journal_mode가 `delete`로 설정되어 있습니다.
- **사용자 영향**: 다수의 사용자가 동시에 `UPDATE`를 수행 시 트랜잭션 충돌로 `database is locked` 오류 발생.
- **해결 방향**: DB 초기화 및 커넥션 시 `PRAGMA journal_mode = WAL;`, `PRAGMA busy_timeout = 5000;` 설정을 활성화하세요.

### [HIGH-2] 16종 썸네일 동시 다운로드 차단
- **파일**: `four-thumbnail/index.html`
- **함수**: `saveAllThumbnails()`
- **정확한 원인**: 타이머(`setTimeout`)를 두고 16개 파일을 연속해서 브라우저 단독 다운로드(`a.click()`)로 처리합니다.
- **사용자 영향**: 브라우저 보안 정책에 의해 다중 다운로드가 차단될 수 있습니다.
- **해결 방향**: `JSZip`을 도입해 16종 이미지를 하나의 ZIP으로 압축해 한 번만 다운로드하도록 UX를 개선해야 합니다.

---

## 4. Medium 문제

### [MEDIUM-1] 작업 디렉토리의 단일 Depth 구조
- **원인**: `data/jobs/beta_job_id` 형태로 모든 폴더를 한 곳에 생성합니다.
- **영향**: 파일 시스템 I/O(조회, 삭제)가 파일 개수에 비례해 느려집니다 (Inode 피크).
- **해결 방향**: `YYYY/MM/DD/user_id/beta_job_id` 형태로 분산해야 합니다.

### [MEDIUM-2] 업로드 용량(Quota) 제한 부재
- **원인**: `beta_create_job`에서 이미지, 비디오 리스트에 대한 갯수/용량 제한이 없습니다.
- **영향**: 대규모 파일 업로드를 악용한 디스크 고갈 공격(DoS)에 취약합니다.

---

## 5. Low 문제

### [LOW-1] DB Index 누락
- **원인**: `beta_jobs` 테이블에 `beta_job_id` PK 외에 어떠한 인덱스도 없습니다.
- **영향**: `ORDER BY created_at DESC` 같은 정렬 시 풀 스캔 발생.

## 6. 저장공간 계산표

작업당 가정: 사진 6장(30MB) + 동영상 0~2개(0~100MB) + 완성결과 및 썸네일 16개(40MB) = 평균 100MB

| 기준 | 최소 | 평균 | 최대 |
| :--- | :--- | :--- | :--- |
| **작업당** | 10MB | 100MB | 300MB |
| **하루 (500건)** | 5GB | 50GB | 150GB |
| **하루 (1,500건)**| 15GB | 150GB | 450GB |
| **7일 (1,500/일)**| 105GB | 1.05TB | 3.15TB |
| **30일 (1,500/일)**| 450GB | 4.5TB | 13.5TB |
| **1년 (1,500/일)**| 5.4TB | 54.7TB | 164TB |

**예상 디스크 고갈 시점**: 로컬 스토리지가 1TB 미만이라면 임시 클립이나 결과물을 매일/매주 단위로 청소하지 않을 시 1~2주일 안에 고갈됩니다.

---

## 7. 부하 병목 지도

- `beta_create_job`: 네트워크 I/O 병목 및 동기 쓰기 블로킹.
- `beta_make_video` / `beta_make_tts`: 서버 CPU 및 RAM 피크.
- 썸네일 `saveAllThumbnails`: 사용자 PC(브라우저) 메모리 누적(OOM).
- `beta_update_job`: 데이터베이스 쓰기 Lock.

---

## 8. 보안 취약점 지도

- **Authentication Bypass** (Critical): API 전반 권한 검증 누락.
- **IDOR** (Critical): URL, Job ID를 통한 타인 작업 훼손.
- **경로 조작 (Path Traversal)**: 결과 객체에 절대 경로가 저장되어 `FileResponse` 서빙 시 검증 없이 노출됨.
- **디스크 고갈 DoS**: Quota 미설정으로 인한 대용량 업로드 폭탄.

---

## 9. 즉시 수정해야 할 상위 10개

1. 라우터 전반 사용자 인증/인가 미들웨어 추가.
2. FFmpeg 렌더링 로직 클라이언트(WASM/WebCodecs) 이관 혹은 큐 분리.
3. SQLite `PRAGMA journal_mode=WAL;` 적용.
4. 비동기 라우터 내 동기 파일 쓰기 루틴 비동기식 청크로 변환.
5. 16종 썸네일 브라우저 ZIP 다운로드 방식으로 변경.
6. 파일 업로드 용량 및 확장자/개수 엄격한 Quota 도입.
7. DB에 `user_id` 컬럼 추가 및 본인 조회 권한 부여.
8. `beta_get_asset` 시 절대 경로 대신 상대 경로 참조 또는 식별자를 이용해 보안 적용.
9. DB 테이블 주요 조회 필드(`created_at`, `status`) Index 설정.
10. 임시 파일 및 실패된 Job의 자동 삭제 스크립트 작성 및 Cron 등록.

## 10. 서비스 시작 전 필수 작업
위의 1~6번 및 10번 청소 스크립트는 오픈 전 무조건 반영해야 서비스 마비를 피할 수 있습니다.

## 11. 서비스 시작 후 1개월 안에 할 작업
디렉토리 파티셔닝(`YYYY/MM/DD`), 사용자 Quota 관리 시스템, 서버-클라이언트 간 성능 폴백 방어 로직.

## 12. 사용자 2,000명 전에 할 작업
오브젝트 스토리지(S3 등) 이전, PostgreSQL로 DB 마이그레이션.

## 13. 현재는 하지 않아도 되는 과잉 설계
Redis 캐싱 시스템, Kubernetes, MSA 분리, 거대한 MQ(RabbitMQ, Kafka 등)는 하루 500~1,500명 규모에서는 과잉 설계입니다.

- `/home/bourne/StoryMaker_1/StoryMaker_beta/app/beta_jobs.py`
- `/home/bourne/StoryMaker_1/storymaker-web/backend/app/static/v1/four-thumbnail/index.html`
- DB 설정/초기화 스크립트

## 15. 최소 수정안
DB WAL 적용, Auth Middleware 추가, 업로드 제한, 브라우저 ZIP 묶음 추가.

## 16. 장기 개선안
서버리스 트랜스코딩 아키텍처 도입 및 S3 오프로딩.

## 17. 검증 계획
K6/Locust를 이용해 10명의 동시 렌더/업로드 시뮬레이션 후 CPU가 죽지 않는지, DB Lock이 없는지 모니터링.

## 18. 분석 완료 후 행동 규칙 답변 (10문 10답)

1. **현재 Dell 한 대로 하루 500명, 동시 10명을 감당할 수 있는가?**
   아니오. 서버 FFmpeg 동기 호출로 인해 CPU가 즉시 마비됩니다.
2. **가장 먼저 터질 가능성이 높은 자원은?**
   CPU(미디어 렌더링)와 DB(SQLite Lock).
3. **작업 1,000개가 하루에 쌓이면 한 달 후 저장공간은 얼마나 필요한가?**
   평균적으로 약 3~4.5TB의 저장공간이 요구됩니다.
4. **어떤 파일을 언제 자동 삭제해야 하는가?**
   렌더 임시 파일 및 실패 작업은 24시간 후, 무료 사용자 결과는 7일 후 삭제해야 합니다.
5. **사용자별 저장공간 제한은 얼마가 적절한가?**
   작업당 200MB, 일일 1GB 내외가 적절합니다.
6. **SQLite는 언제까지 유지 가능한가?**
   WAL 모드와 적절한 Timeout만 적용하면 하루 1,500명 규모(현재 단계)까지는 안정적입니다.
7. **PostgreSQL 전환 시점은 언제인가?**
   동시 다중 API 서버 운용이 필요하거나, 일일 작업이 5,000건을 넘을 때 전환해야 합니다.
8. **로컬 디스크에서 오브젝트 스토리지로 이전할 시점은 언제인가?**
   트래픽 증가와 무관하게, 로컬 디스크 70% 고갈(약 1개월 뒤 예상) 전 이전을 시작해야 합니다.
9. **16종 썸네일 구조에서 아직 남은 가장 큰 지뢰는 무엇인가?**
   16회 연속 `a.click()` 다운로드로 인한 브라우저 보안 차단(Spam Block)입니다.
10. **서비스 공개 전에 반드시 고쳐야 하는 상위 5개는 무엇인가?**
   ① 전역 인증 결함(IDOR) 조치, ② 서버측 FFmpeg -> 클라이언트 WASM 이관 (또는 큐 분리), ③ SQLite WAL 활성화, ④ 블로킹 업로드 루틴 비동기화, ⑤ 파일 크기 및 개수 제한(Quota).
