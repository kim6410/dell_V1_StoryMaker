## 14. 아직 100% 복구로 확정할 수 없는 이유

복구 자료는 대부분 확보됐지만, 새 Ubuntu 서버 또는 격리 VM에서 다음 전 과정을 아직 실제 완주하지 않았습니다.

```text
Git clone
비공개 백업 원위치 복사
파일 권한과 소유권 복구
Python 환경 재구성
Docker 이미지 재빌드
Caddy·외부 도메인 연결
V1 로그인
회원·업체정보 표시
기존 V1 보관함 표시
Beta 제작 화면 연결
API 콘텐츠 생성
음성·이미지·MP4 생성
기존 Beta 보관함 열람
서버 재부팅 후 자동 시작
```

따라서 현재 판정은 다음과 같습니다.

```text
복구에 필요한 핵심 자료 확보: 완료
자동 비공개 백업: 완료
GitHub 원격 보존 검증: 완료
DB 무결성 검증: 완료
깨끗한 환경 실복구 모의훈련: 미완료
100% 완전 복구 보증: 모의훈련 전에는 확정 불가
```


## 15. 다음 작업 권장 순서

1. 운영 서비스와 분리된 테스트 VM 또는 별도 복구 폴더를 준비합니다.
2. GitHub 저장소를 새 위치에 clone합니다.
3. `FULL_SERVER_RECOVERY.md` 순서대로 비공개 백업을 원위치에 복원합니다.
4. Docker Compose와 systemd 서비스를 테스트 전용 포트로 시작합니다.
5. V1 로그인부터 Beta MP4 제작과 기존 보관함 열람까지 E2E 검증합니다.
6. 서버 재부팅 후 자동 실행을 확인합니다.
7. 실제 복구 중 빠진 파일과 명령을 복구 문서에 반영합니다.
8. 모든 항목 PASS 후 해당 스냅샷을 완전 복구 기준본으로 지정합니다.


## 16. 절대 주의사항

운영 서버에서 복구 시험을 바로 실행하지 않습니다.

기존 V1·Beta 서비스와 동일한 포트로 테스트 서비스를 실행하지 않습니다.

실제 DB를 덮어쓰기 전에 반드시 서비스 중지와 추가 백업을 수행합니다.

Git에 실제 `.env`, API 키, 사용자 DB, 사용자 결과물을 커밋하지 않습니다.

비공개 백업 폴더는 사용자 승인 없이 삭제하거나 정리하지 않습니다.

Tampermonkey 설치와 Gemini 로그인 쿠키는 자동 복구 대상이 아닙니다.

브라우저 방식을 사용할 경우 복구 후 Worker 재설치와 Gemini 재로그인이 필요합니다.
