## 12. 남은 보안 검토 사항

현재 limiter는 단일 컨테이너 메모리 기반이다.

컨테이너 재시작 시 기록이 초기화되고, 향후 Uvicorn worker가 여러 개가 되면 프로세스마다 제한 기록이 분리된다.

현재 단일 인스턴스에서는 동작하지만 장기적으로 Redis 또는 DB 기반 저장소가 필요하다.

여러 사용자가 동일한 공인 IP를 공유하는 회사·매장·모바일 통신망 환경에서 IP 제한이 먼저 걸릴 가능성이 있으므로 실제 운영 로그를 보고 기준값을 조정해야 한다.

비밀번호 최종 재설정은 WordPress가 담당하므로 V1만으로 전체 공격 경로가 보호되는 것은 아니다.

WordPress의 `wp-login.php?action=lostpassword`, 회원가입, StoryMaker 로그인 플러그인에도 별도 Rate Limit 또는 보안 플러그인 정책이 적용되어 있는지 확인해야 한다.

V1의 비밀번호 변경 API는 로컬 Argon2 해시를 바꾸지만 일반 로그인 원장은 WordPress이므로 두 비밀번호 원장의 정합성 문제도 별도 해결 대상이다.

### admin/admin 위험 판정 정정

로컬 DB에는 다음 레거시 계정이 남아 있다.

- `users.id=1`
- `username=admin`
- `role=admin`
- `is_active=1`
- `auth_provider=local`
- `wordpress_user_id=NULL`
- 레거시 SHA-256 형식 비밀번호 해시

그러나 현재 `/api/auth/login`은 `guest/guest`만 로컬 예외 처리하고, `admin`을 포함한 일반 계정은 WordPress `/wp-json/storymaker/v1/login`으로 인증한다.

실제 `admin/admin` 로그인 요청 결과는 HTTP 400, `아이디 또는 비밀번호가 일치하지 않습니다.`였다.

프로젝트 전체 검색에서도 `verify_password()`는 로그인 경로가 아니라 `/auth/change-password`에서만 호출된다.

따라서 `admin/admin으로 지금 즉시 관리자 로그인 가능`이라는 기존 판단은 오탐으로 정정한다.

`users.id=1`의 세션은 0개이며, 실제 운영 관리자 계정은 `users.id=82`, `rinsoo641022@gmail.com`, `auth_provider=wordpress`, `wordpress_user_id=1`이다.

### users.id=1 데이터 참조

34개 테이블 중 사용자 ID 계열 컬럼을 가진 15개 테이블을 조회한 결과, `users.id=1`을 참조하는 데이터는 `v1_nemotron_conversations` 3건뿐이었다.

해당 3건은 테스트성 대화이며 SQL 외래키 제약이 없어 계정을 삭제하면 고아 행으로 남는다.

따라서 현재는 삭제하지 않고 보류하며, 향후 정리 시 소유권 이전 또는 명시적 정리 후 비활성화하는 것이 안전하다.

### JWT 발급 경로

JWT 발급 경로는 다음 3개로 확인됐다.

1. `/auth/login`
2. `/auth/google`
3. `/auth/local-exchange`

세 경로 모두 `session_id` 클레임을 포함한다.

### 세션-토큰 사용자 결합 누락

`get_current_user()`와 `get_optional_current_user()` 모두 세션 존재와 `logout_at`만 확인하고 다음 소유권 검증은 하지 않는다.

- `session_rec.user_id == user.id`
- `payload.sub == user.id`

현재 JWT 서명키를 모르면 직접 악용하기 어렵지만, 서명키 유출 또는 내부 토큰 오용 상황에서는 다른 사용자의 유효 세션 ID를 결합할 여지가 있으므로 최소 패치 대상이다.

다음 수정 시 두 함수에서 `payload.sub`, `payload.username`, DB 사용자 ID, `session_rec.user_id`가 모두 일치하도록 검증한다.

### 세션 정리 정책

DB에는 `logout_at IS NULL` 세션이 25건 남아 있었고 가장 오래된 것은 2026-07-14 세션이었다.

JWT 자체는 24시간 `exp`로 만료되므로 오래된 DB 세션 레코드만으로 실제 인증이 계속되는 것은 아니다.

현재 문제는 즉시 인증 우회가 아니라 DB 누적, 활성 세션 표시 부정확, 세션 관리 어려움으로 분류한다.
