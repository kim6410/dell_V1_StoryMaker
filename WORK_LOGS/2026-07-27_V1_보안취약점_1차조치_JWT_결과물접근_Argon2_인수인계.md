### 2.2 Nginx 외부 라우팅 확인

확인된 V1 프록시 경로:

- `/v1-api/*` → 8011
- `/static/v1/*` → 8011
- `/v1/*` → 8011

`/data/output_results/*` 외부 프록시 규칙은 없다.

결론:

- 내부 `127.0.0.1:8011/data/output_results/...`는 당시 무인증 200이었다.
- 외부 `app.mystorymaker.net/data/output_results/...`는 404였다.
- 이후 내부 접근도 인증·소유권 검증 방식으로 차단했다.

### 2.6 비밀번호 Argon2id 마이그레이션 기반 적용

수정 파일:

- `storymaker-web/backend/app/core/security.py`
- `storymaker-web/backend/requirements.txt`

적용 내용:

- 신규 `hash_password()`는 Argon2id를 생성한다.
- Argon2 설정은 memory_cost=65536, time_cost=3, parallelism=4이다.
- `verify_password()`는 Argon2id와 기존 SHA-256 64자리 해시를 모두 검증한다.
- 신규 로컬 사용자, 비밀번호 변경, WordPress·Google shadow 사용자 무작위 비밀번호는 Argon2id로 저장된다.
- 기존 SHA-256 사용자는 평문을 알 수 없으므로 강제 변환하지 않았다.
- `argon2-cffi>=23.1.0,<26.0.0`을 requirements에 추가하고 Docker 이미지를 다시 빌드했다.

중요 구조:

- 현재 일반 로그인 원장은 WordPress이다.
- WordPress 로그인 성공 시 로컬 비밀번호 해시를 검증하지 않으므로 로그인만으로 기존 SHA-256이 자동 승격되지는 않는다.
- 기존 사용자가 V1 비밀번호 변경 경로를 사용하거나 향후 인증 원장 통합을 할 때 Argon2id로 전환된다.

백업:

- `/home/bourne/StoryMaker_1/Backup/20260727_052547_V1_password_hash_argon2_before_apply`

## 5. 다음 작업 우선순위

다음 단계는 로그인·회원가입 Rate Limit 적용이다.

권장 범위:

1. `/api/auth/login`
2. WordPress 회원가입 연동 요청 경로
3. 비밀번호 찾기·재설정 요청 경로
4. Google 로그인 실패 반복 경로

안전한 적용 원칙:

- IP 기준과 계정명 기준을 분리한다.
- 로그인 성공은 과도하게 제한하지 않는다.
- 역방향 프록시의 `X-Forwarded-For` 신뢰 범위를 확인한다.
- 일반 API 전체에 일괄 Rate Limit을 걸지 않는다.
- 초기 권장치는 로그인 실패 5회/5분, 비밀번호 찾기 3회/15분 수준으로 시작하되 실제 운영 흐름 확인 후 확정한다.
- 메모리 기반 limiter는 컨테이너 재시작 시 초기화되므로 현재 단일 인스턴스에는 가능하지만 장기적으로 Redis 또는 DB 기반을 검토한다.
- 적용 전 로그인·WordPress 인증·Google 로그인·비밀번호 변경 경로를 다시 지도화한다.
