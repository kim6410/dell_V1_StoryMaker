## 1. 이번 단계의 목적

로그인·회원가입·메일 인증·비밀번호 변경 및 찾기·로그아웃·회원관리의 실제 요청 경로를 먼저 확정한다.

V1 화면에서 공용 인증 자산과 V1 전용 인증 자산이 혼재하는지 확인하고, WordPress 사용자와 V1 로컬 사용자 사이의 책임 범위를 분리한다.

근거가 확정되기 전에는 운영 인증 코드와 DB를 수정하지 않는다.

## 2. 현재 인증 주체

현재 인증 구조에는 다음 세 계층이 동시에 존재한다.

1. Hostinger WordPress
   - 실제 회원 원장 역할
   - WordPress 사용자 ID와 로그인 비밀번호를 보유
   - `storymaker-auth` REST 엔드포인트를 통해 로그인·가입 기능 제공

2. Dell V1 FastAPI
   - `/v1-api/auth/*` 요청 처리
   - WordPress 로그인 성공 후 V1 로컬 shadow user를 조회하거나 생성
   - JWT 및 V1 세션·활동 로그 처리

3. 공용 프런트 인증 스크립트
   - `/static/app_auth.js`
   - `/api/auth/*`를 호출
   - V1 전용 `/v1-api/auth/*`가 아닌 기본 upstream 인증 경로를 사용

## 3. 기능별 실제 인증 경로

### 3.1 로그인

V1 정상 경로:

`V1 React 또는 V1 전용 화면`
→ `POST /v1-api/auth/login`
→ Dell V1 FastAPI `app/api/auth.py`
→ Hostinger WordPress `POST /wp-json/storymaker/v1/login`
→ WordPress 사용자 인증
→ 응답의 `wordpress_user_id`로 V1 로컬 사용자를 조회 또는 생성
→ V1 JWT·쿠키·세션 발급

확인 근거:

- `app/api/auth.py` 약 388행: `POST /auth/login`
- 약 415행: WordPress 로그인 URL 호출
- 약 456행: WordPress 로그인 성공 후 V1 로컬 사용자 생성 가능
- 약 549행: `GET /auth/me`

충돌 경로:

`/static/app_auth.js`
→ `POST /api/auth/login`

공용 스크립트가 V1 화면에서 실행되면 V1 백엔드 8011이 아니라 기본 upstream으로 전달될 수 있다.

### 3.2 회원가입

현재 V1 FastAPI 직접 가입 경로:

`POST /v1-api/auth/join`
→ `app/api/auth.py`
→ HTTP 400으로 차단
→ WordPress 회원가입 사용을 안내

확인 근거:

- `app/api/auth.py` 약 559행: `POST /auth/join`
- 해당 라우터는 WordPress 연동 개편 이후 직접 가입을 차단

현재 공개 가입 경로:

`V1 또는 공용 로그인 모달의 회원가입 선택`
→ WordPress 가입 화면 또는 WordPress `storymaker-auth` 등록 REST
→ WordPress `register_new_user()` 실행
→ `wp_users` 사용자 생성

핵심 문제:

기존 WordPress 플러그인은 메일 전달 성공을 가입 완료 조건으로 사용하지 않는다.

메일 발송에 실패해도 WordPress 사용자가 먼저 생성될 수 있으며, 응답 메타데이터의 `email_verified=true`가 실제 검증 결과를 뜻하지 않는다.

### 3.3 메일 인증

현재 확정 상태:

- 가입 전 이메일 소유권 검증 단계가 없다.
- 인증 토큰 검증 완료 후에만 `wp_users`를 생성하는 pending 구조가 없다.
- 기존 플러그인의 `email_verified=true`는 실제 메일 인증 결과가 아니다.
- V1 로컬 `User` 모델에는 이메일 인증 상태를 안전하게 표현할 필드가 없다.

따라서 현재 화면에 표시되는 가입 완료와 실제 이메일 소유권 확인은 같은 의미가 아니다.

### 3.4 비밀번호 변경과 비밀번호 찾기

V1 FastAPI 내부 변경 경로:

`PUT /v1-api/auth/change-password`
→ 현재 로그인된 V1 로컬 사용자의 `password_hash` 변경

확인 근거:

- `app/api/auth.py` 약 570행: `PUT /auth/change-password`
- 약 580행: 현재 비밀번호 검증
- 약 586행: V1 로컬 비밀번호 해시 변경

구조적 위험:

실제 로그인 원장은 WordPress인데 V1 로컬 shadow user의 비밀번호만 변경하면, 다음 WordPress 로그인에는 반영되지 않는다.

공용 스크립트 경로:

`/static/app_auth.js`
→ `PUT /api/auth/change-password`

비밀번호 찾기와 재설정은 WordPress reset token 흐름과 V1 화면 흐름이 하나의 경로로 통합되어 있지 않다.

따라서 비밀번호 변경과 비밀번호 찾기는 WordPress를 단일 원장으로 정한 뒤 다시 연결해야 한다.

### 3.5 로그아웃

V1 정상 경로:

`POST /v1-api/auth/logout`
→ V1 쿠키 제거
→ V1 세션 종료 및 로그 기록

확인 근거:

- `app/api/auth.py` 약 611행: `POST /auth/logout`

충돌 경로:

`/static/app_auth.js`
→ `POST /api/auth/logout`

V1 화면에서 공용 로그아웃 함수가 실행되면 V1 쿠키·세션과 다른 upstream 세션 중 일부만 종료될 가능성이 있다.

### 3.6 회원관리

V1 관리자 화면 정상 경로:

`admin-member-bridge.js`
→ `GET /v1-api/auth/me`로 관리자 권한 확인
→ `GET /v1-api/admin/members`
→ Dell V1 `app/api/admin_members.py`
→ V1 로컬 사용자·페르소나·과금 정보와 WordPress 사용자 조회 결과를 조합

확인 근거:

- `static/v1/admin-member-bridge.js` 약 190행: `/v1-api/admin/members`
- 약 218행: 회원별 과금 요약
- 약 308행: 회원별 페르소나
- 약 484행: `/v1-api/auth/me`
- `app/api/admin_members.py` 약 185행: `GET /admin/members`
- 약 49행: WordPress REST `/users` 조회

현재 장애:

WordPress 사용자 목록 동기화가 HTTP 401을 반환한 기록이 있다.

그 결과 V1 로컬 사용자와 WordPress 회원 원장을 한 화면에서 완전하게 대조하지 못한다.

## 4. 확정된 충돌지점

### 충돌 1. 인증 API prefix 이중화

- V1 전용: `/v1-api/auth/*`
- 공용 스크립트: `/api/auth/*`

같은 화면에서 두 prefix가 함께 실행될 수 있다.

### 충돌 2. 인증 모달 제어 함수 중복

`auth_modal_unified.js`와 `app_auth.js`가 로그인 모달 생성·열기·탭 전환·상태 표시를 각각 제어한다.

DOM 소유자가 하나가 아니므로 모달이 뒤섞이거나 다른 API가 호출될 수 있다.

### 충돌 3. 회원가입 책임 불명확

V1 `/auth/join`은 차단되어 있지만, WordPress 공개 가입 화면과 플러그인 REST 가입 기능은 별도로 살아 있다.

화면상 회원가입과 실제 사용자 생성 시점이 일치하지 않는다.

### 충돌 4. 이메일 인증 상태 허위 확정 가능성

실제 메일 인증 토큰 검증 없이 `email_verified=true`가 반환될 수 있다.

메일 전송 성공 여부와 사용자 생성 여부도 분리되어 있지 않다.

### 충돌 5. 비밀번호 원장 불일치

WordPress가 실제 로그인 원장인데 V1 로컬 비밀번호 변경 API가 별도로 존재한다.

두 비밀번호가 달라질 수 있다.

### 충돌 6. 사용자 ID 연결 위험

WordPress 사용자 ID와 V1 로컬 사용자 ID는 같은 숫자라고 가정할 수 없다.

연결 기준은 명시적 `wordpress_user_id`여야 하며 이메일이나 숫자 ID 단독 추정은 금지한다.

### 충돌 7. 회원관리 WordPress 조회 401

관리자 회원 화면은 WordPress REST 사용자 목록을 불러와야 하지만 인증 설정 불일치로 401이 발생할 수 있다.

## 5. 권장 단일 인증 경로

### 로그인

`V1 모달`
→ `/v1-api/auth/login`
→ WordPress 로그인 검증
→ V1 shadow user 연결
→ V1 JWT 발급

### 회원가입

`V1 모달`
→ `/v1-api/auth/registrations/request`
→ pending registration 생성
→ 인증 메일 발송
→ 토큰 검증 성공
→ 그 시점에만 WordPress 사용자 생성
→ V1 로그인 화면으로 복귀

### 비밀번호 찾기·재설정

`V1 모달`
→ `/v1-api/auth/password-reset/request`
→ WordPress 기준 reset token 발급
→ 검증 후 WordPress 비밀번호 변경
→ 기존 V1 세션 무효화

### 로그아웃

`V1 모달`
→ `/v1-api/auth/logout`
→ V1 쿠키·로컬 저장 토큰·서버 세션을 한 번에 정리

### 회원관리

`V1 관리자 화면`
→ `/v1-api/admin/members`
→ WordPress ID를 기준으로 V1 shadow user·페르소나·과금 프로필 조합

## 6. 다음 수정의 최소 범위

1. V1 화면의 인증 자산과 모든 인증 호출을 `/v1-api/auth/*`로 단일화한다.
2. 모달 DOM과 상태 제어는 V1 전용 컨트롤러 한 곳만 소유하도록 한다.
3. 공용 upstream의 `/static/app_auth.js`, `/static/auth_modal_unified.js`는 수정하지 않는다.
4. V1 로컬 `change-password`를 그대로 노출하지 않고 WordPress 원장 기준 재설정 흐름으로 교체한다.
5. WordPress 사용자 목록 조회 401 원인을 별도 복구한 뒤 회원관리 정합성을 검증한다.
6. pending registration은 별도 테이블로 만들고 인증 성공 전 `wp_users`를 생성하지 않는다.
