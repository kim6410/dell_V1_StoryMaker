  ```python
      return hash_obj.hexdigest()
  ```
- **실제 운영 경로 여부**: 예. `User.password_hash` 저장/검증에 실제 사용됨(`auth.py`의 로그인·비밀번호 변경 경로에서 `verify_password`/`hash_password` 호출).
- **재현 근거**: 코드 열람으로 확정. 실제 DB의 해시값을 크랙 시도하지는 않았음(DB 데이터 변경·부하 유발 금지 원칙 준수).
- **오탐 가능성**: 낮음. salt가 모든 사용자에 대해 동일한 상수이고, SHA-256은 GPU로 초당 수십억 회 계산 가능한 고속 해시로 비밀번호 저장용으로 부적절함이 코드로 명확히 확인됨.
- **영향 범위**: DB(`storymaker.db`)가 어떤 경로로든(백업 노출, 다른 취약점과 결합) 유출될 경우 전체 회원 비밀번호가 사전대입·레인보우테이블 공격에 취약. 동일 비밀번호를 쓰는 사용자끼리 해시가 동일해 패턴 노출.
- **CRITICAL 등급 근거 (단독 vs 결합)**: 이 항목을 **단독으로만** 평가하면 "탈취 전제 조건(DB 유출)이 별도로 필요하다"는 점에서 HIGH가 합리적이다. 그러나 이번 조사에서 함께 확인된 CRIT-1(운영 JWT 서명 키가 Git에 평문 커밋되어 사실상 이미 유출된 것과 동등한 상태)과 CRIT-3(`/data/output_results` 무인증 노출로 백업·산출물 파일이 실제로 인증 없이 외부에 열람 가능함을 재현 확인)이 "DB 또는 민감 파일이 외부로 노출될 수 있는 실질적 경로"를 이미 열어 둔 상태이므로, 그 경로를 통해 DB가 노출되면 이 취약한 해시 방식이 **즉시 전수 크랙으로 직결**된다. 즉 이 보고서는 CRIT-2를 **CRIT-1·CRIT-3과 결합했을 때의 실질 위험을 기준으로 CRITICAL로 유지**했으며, 만약 CRIT-1·CRIT-3이 먼저 해결되어 DB·파일 유출 경로가 차단된다면 이 항목의 등급은 HIGH로 재평가할 수 있다.
- **권장 수정 방향**: bcrypt 또는 argon2로 교체하고 사용자별 랜덤 salt 적용. 기존 해시는 로그인 성공 시점에 새 알고리즘으로 재해싱(lazy migration)하거나, 전체 강제 비밀번호 재설정 캠페인 진행.
- **수정 시 연쇄 장애 위험**: 기존 해시 포맷과 신규 포맷이 공존해야 하므로 `verify_password`에 포맷 판별 로직 필요(예: 해시 접두사로 알고리즘 구분). 잘못 구현 시 기존 사용자 전원 로그인 실패 가능 — **고위험 작업으로 분류, 반드시 사전 DB 백업 및 단계적 배포 필요**.
- **검증 방법**: 기존 계정 로그인 유지 확인 + 신규 가입 계정이 새 알고리즘으로 저장되는지 DB 조회(SELECT만, 값 마스킹)로 확인.
- **롤백 기준**: 로그인 실패율 급증 시 이전 `hash_password`/`verify_password` 코드로 즉시 롤백. DB에 이미 재해싱된 사용자가 있다면 롤백 시 해당 사용자만 재로그인 필요.

- **수정 시 연쇄 장애 위험**: 기존 가입 플로우와 병행 운영 필요, 기존 사용자에게 소급 적용 금지(인용 출처 문서 §7 절대 금지 사항과 동일).
- **검증 방법**: pending registration 도입 후 미인증 상태에서는 WordPress 사용자가 생성되지 않는지 실제 가입 시나리오로 확인(운영 반영 후).
- **롤백 기준**: 정상 가입 완료율이 급락하면 즉시 이전 방식으로 복원.

- **검증 방법**: 재설계 후 V1 비밀번호 변경이 WordPress 로그인에도 즉시 반영되는지 확인.

### CONF-6. 로그인/가입 API에 Rate Limit·계정 잠금 정책 부재

- **위험도**: MEDIUM
- **파일/줄번호**: `storymaker-web/backend/app/api/auth.py` 전체 — `slowapi`, `Limiter`, 시도 횟수 카운터 등 부재를 전수 grep으로 확인(검출 0건)
- **실제 운영 경로 여부**: 예.
- **재현 근거**: 코드/의존성 grep으로 확인(`slowapi|RateLimit|rate_limit|Limiter` 전체 프로젝트 검색 결과 없음). 실제 브루트포스 요청을 반복 전송해 계정을 잠그거나 서비스에 부하를 주는 실행은 하지 않았음.

- **영향 범위**: 로그인 브루트포스, 가입 폼 남용(스팸 계정 대량 생성) 방어 부재.
- **권장 수정 방향**: `slowapi` 또는 동등한 IP/계정 기준 Rate Limit 미들웨어 추가, 연속 실패 시 지수 백오프 또는 일시 잠금.
- **수정 시 연쇄 장애 위험**: 정상 사용자의 재시도가 과도하게 차단되지 않도록 임계값 튜닝 필요. 프록시 뒤에서는 클라이언트 IP 판별에 `X-Forwarded-For` 신뢰 설정을 정확히 해야 함(잘못 설정 시 전체 요청이 동일 IP로 취급되어 오탐 가능).
- **검증 방법**: 정상 로그인 빈도에서는 차단되지 않고, 임계값 초과 시 429 등 명확한 응답이 오는지 확인.
- **롤백 기준**: 정상 사용자 다수가 차단되는 회귀 발생 시 즉시 비활성화 후 임계값 재조정.

### CONF-7. 인증 쿠키 도메인이 `.mystorymaker.net` 전체에 공유됨

- **위험도**: MEDIUM
- **파일/줄번호**: `storymaker-web/backend/app/api/auth.py:39` — `AUTH_COOKIE_DOMAIN = ".mystorymaker.net"`, `_auth_cookie_scope`(63-71행)에서 `hostname.endswith(".mystorymaker.net")`이면 이 도메인으로 쿠키 스코프 설정
- **실제 운영 경로 여부**: 예.
- **재현 근거**: 코드 열람으로 확정. 실제로 다른 서브도메인에서 쿠키가 전송되는지 브라우저 테스트는 수행하지 않았음(추가 로그인 세션 생성 없이는 검증 불가하며, 실제 로그인은 지시에 따라 수행하지 않음).
- **오탐 가능성**: 낮음(쿠키 domain 속성 자체는 코드로 확정). 실제 악용 가능성은 다른 서브도메인의 보안 상태에 종속(SUSPECTED로 분류할 부분은 §3 참조).

- **권장 수정 방향**: 쿠키 domain을 `app.mystorymaker.net` 단일 호스트로 좁히거나(서브도메인 SSO가 실제로 필요하지 않다면), SSO가 필요하다면 각 서브도메인의 보안 수준을 동일하게 높인 뒤 유지.
- **수정 시 연쇄 장애 위험**: 만약 다른 서브도메인이 실제로 이 쿠키를 공유해 SSO처럼 동작하고 있었다면, 범위를 좁힐 경우 해당 기능이 깨질 수 있음 — 변경 전 실제 사용 여부 확인 필요.
- **검증 방법**: 변경 후 V1 로그인이 정상 유지되는지, 의도된 서브도메인 간 세션 공유가 실제로 필요했는지 재확인.
- **롤백 기준**: 의도된 기능이 깨지면 원래 도메인 스코프로 복원.

### CONF-8. 다수의 무분별한 `except Exception:` 패턴 (실패 은폐 위험)

- **위험도**: MEDIUM(개별 사례 확인 시 HIGH로 상향 가능)
- **파일/줄번호**: 전체 `app/` 트리에서 `except Exception:` 단독(구체 예외 미지정, 변수 미바인딩) 패턴 **199건** 검출(`grep -rn "except Exception:\s*$" --include=*.py .` 결과). 대표 예: `main.py:104-109`(시작 시 유지보수 함수 실패를 print만 하고 무시).
- **실제 운영 경로 여부**: 예(다수가 실제 요청 처리 경로에 위치).
- **재현 근거**: 정적 grep 카운트로 확정. 이 중 "실패를 성공으로 위장 반환"하는 구체 사례까지 전수 확인하지는 않았음(표본 확인 수준).
- **오탐 가능성**: 중간. 199건 모두가 실제 장애로 이어지는 것은 아니며(정상적으로 무해한 fallback도 포함), 개별 사례별 위험도 판단은 추가 조사 필요.
- **영향 범위**: 특정 단계 실패 시에도 API가 200을 반환하거나 완료 상태로 기록될 가능성 — Podcast/MP4/썸네일 등 다단계 생성 파이프라인에서 특히 위험(§4 지뢰 항목과 연결).
- **권장 수정 방향**: 최소한 로그에 예외 내용을 남기도록(`except Exception as exc: logger.exception(...)`) 일괄 개선, 상태값을 완료로 확정하기 전 실제 산출물 존재·크기 검증 로직 강화.
- **수정 시 연쇄 장애 위험**: 예외를 노출시키면 기존에 "조용히 넘어가던" 경로가 사용자에게 에러로 노출될 수 있어, 무해한 것과 실제 위험한 것을 구분하는 신중한 개별 검토가 필요(일괄 치환 금지 — 00_READ_FIRST 9번 원칙과 일치).
- **검증 방법**: 각 수정 지점별로 실패 유도 테스트 후 로그 기록 여부와 사용자 응답 변화 확인.
- **롤백 기준**: 로그 추가로 인한 성능 저하나 예상치 못한 예외 노출 발생 시 해당 지점만 개별 롤백.

### CONF-9. CSRF 방어가 `SameSite=Lax` 단독 의존, 별도 CSRF 토큰 부재

- **위험도**: MEDIUM
- **파일/줄번호**: `storymaker-web/backend/app/api/auth.py:74-101`(`_set_auth_cookie`/`_clear_auth_cookie`, `samesite="lax"`만 설정) — 전체 `app/api/*.py`에서 CSRF 토큰 검증 로직 grep 결과 검출 0건.
- **실제 운영 경로 여부**: 예.
- **재현 근거**: 코드/설정 열람 및 grep으로 확인. 실제 크로스사이트 요청 위조 공격을 재현하지는 않았음.
- **오탐 가능성**: 낮음(CSRF 토큰 부재 자체는 확정). 다만 `SameSite=Lax`가 일반적인 크로스사이트 POST 요청은 상당 부분 차단하므로 실질 악용 난이도는 있음 — "부재"는 확정, "실제 악용 성공 여부"는 미실행.
- **영향 범위**: 상태 변경 API(예: 비밀번호 변경, 관리자 작업)가 이론상 크로스사이트 GET 기반 트리거나 `SameSite` 우회 시나리오에 노출될 수 있음.
- **권장 수정 방향**: 상태 변경 API에 CSRF 토큰 검증 추가 또는 `SameSite=Strict` 검토(단, Strict는 서브도메인 간 이동 시 쿠키 미전송으로 사용성 영향 가능).
- **수정 시 연쇄 장애 위험**: `SameSite=Strict`로 변경 시 외부 링크를 통한 최초 진입 시 로그인 상태가 유지되지 않을 수 있음 — 기존 사용자 흐름 회귀 테스트 필요.
- **검증 방법**: 변경 후 정상 사용자 흐름(로그인 유지, 외부 링크 진입)이 깨지지 않는지 확인.
- **롤백 기준**: 사용성 회귀 발생 시 이전 설정으로 복원.

## 4. 지뢰 구간 (보안 이외 구조적 위험)

- **중복 데드 코드 파일**: `api/mobile_one_shot - 07201021.py`, `api/slideshow - 07201021.py`(파일명에 공백·날짜 포함)가 `api/` 디렉토리에 실제 사용 파일과 나란히 존재. `main.py`의 import 목록에는 포함되지 않아 **현재 미사용으로 추정**되나, 파일명이 유사해 향후 실수로 잘못된 파일을 수정할 위험이 있음. 삭제 전 실제 미사용 여부 재확인 필요(00_READ_FIRST 10번 절차 준수 대상).
- **인증 자산 이중화 잔존**: `/static/app_auth.js`, `/static/auth_modal_unified.js`(공용) vs `/static/v1/auth/*`(V1 전용, 오늘 분리 작업 완료)가 공존. `index.html`이 현재 어느 쪽을 로드하는지는 오늘자 작업 로그로 V1 전용 경로로 전환 완료된 것으로 확인되나, 캐시나 이전 배포본이 남아있는 환경에서는 재혼선 가능.
- **Git 미추적 상태의 운영 핵심 파일 다수**: `git status`에서 `storymaker-web/backend/app/static/v1/*.js` 다수와 `admin-member-bridge.js` 등이 미추적 상태로 확인됨 — 이는 보안 취약점은 아니나, Git으로 변경 이력 추적이 안 되는 상태이므로 실수로 덮어써도 diff로 복구 불가. `.gitignore` 재검토 및 필요한 파일의 Git 추적 편입 권장(사용자 승인 필요 사항, 이번 보고서는 발견만 기록).

(참고: `supertonic3-api.service` 크래시 루프는 보안·구조 지뢰가 아니라 서버 공유 리소스 관점의 별도 참고 항목이므로 CONF-11(§2)로 이동해 정식 위험도 분류에 포함했다. 이 지뢰 구간(§4)에는 LOW 3건만 유지한다.)
