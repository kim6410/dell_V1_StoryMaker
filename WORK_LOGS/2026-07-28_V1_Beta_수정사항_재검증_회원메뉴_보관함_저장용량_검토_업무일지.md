## 3. 핵심 발견 — 마이페이지 비밀번호 변경이 여전히 실패하는 진짜 원인

### 3.1 코드 재검증

`git show 6ba02f4 -- storymaker-web/backend/app/api/auth.py`로 전체 diff를 확인했다. `change_password()`가 이제 다음 순서로 동작하도록 올바르게 재작성되어 있다.

1. 새 비밀번호 8자 이상, 현재 비밀번호와 동일하지 않은지 검사
2. `wordpress_user_id`가 있으면 WordPress 계정으로 판단
3. `POST /wp-json/storymaker/v1/login`으로 현재 비밀번호 재검증
4. **`POST {WORDPRESS_API_URL}/users/{wordpress_user_id}` (WordPress REST, Application Password Basic Auth)로 실제 비밀번호 변경 요청**
5. 성공 시 해당 사용자의 열린 세션을 전부 `logout_at` 처리(전 기기 로그아웃)하고 인증 쿠키 삭제

코드 로직 자체는 §2에서 지적한 CITED-2/BUG-AUTH-001 문제를 정확히 해결하는 방향으로 구현되어 있다.

### 3.2 실제 재현 — 근본 원인은 V1 코드가 아니라 WordPress 자격증명

`storymaker-v1-backend` 컨테이너 내부에서, **부작용 없는 GET 요청만으로** Application Password의 유효성을 직접 확인했다(비밀번호 값은 어디에도 출력하지 않음).

```
GET https://mystorymaker.net/wp-json/wp/v2/users/me?context=edit
Authorization: Basic (WORDPRESS_USERNAME + WORDPRESS_APP_PASSWORD)
→ HTTP 401
{"code":"rest_not_logged_in","message":"현재 로그인 상태가 아닙니다.","data":{"status":401}}
```

**결론**: 현재 `.env`에 등록된 `WORDPRESS_APP_PASSWORD`(Application Password)가 WordPress REST API에서 거부되고 있다. `change_password()`의 4단계(`update_resp`)가 이 자격증명으로 `POST /users/{id}`를 호출하므로, 이 시점에서 401이 발생해 `HTTPException(502, "WordPress 비밀번호 변경에 실패했습니다.")`로 귀결된다. 1단계(로그인 검증)는 다른 엔드포인트(`storymaker/v1/login`)를 쓰므로 정상 통과한다 — 즉 "현재 비밀번호는 맞다고 나오는데 새 비밀번호로 바뀌지는 않는" 사용자 체감 증상과 정확히 일치한다.

이 문제는 이전 감사보고서의 **CITED-3(WordPress 사용자 목록 401)와 동일한 근본 원인**이며, V1 코드가 아니라 **WordPress 관리자 화면에서 Application Password를 재발급**해야 해결된다.

### 3.3 조치 필요 사항 (미실행, 사용자 승인 및 WordPress 관리자 작업 필요)

1. Hostinger WordPress 관리자 → 사용자 프로필(`WORDPRESS_USERNAME` 계정) → Application Passwords에서 새 자격증명 발급
2. `.env`의 `WORDPRESS_APP_PASSWORD` 교체
3. `storymaker-v1-backend` 컨테이너 재시작
4. 재발급 후 동일한 안전한 GET 요청(`/users/me?context=edit`)으로 200 확인
5. 테스트 계정으로 실제 비밀번호 변경 E2E 재확인

## 4. 관리자 전용 "회원관리" 메뉴 미표시 문제 조사

### 4.1 사용자 증상

### 4.2 코드 조사 결과

관련 파일: `storymaker-web/backend/app/static/v1/admin-member-bridge.js`, `v1-admin-member-menu-color.js`, `index.html`

- `index.html`의 `<style>[data-storymaker-member-menu]:not([data-storymaker-admin-authorized="1"]){display:none!important}` 규칙은 정적 마크업이 아니라 **JS가 동적으로 생성하는 요소**에 대한 게이트다.
- `admin-member-bridge.js`의 `createMenu()`는 좌측 메뉴에서 "사용현황"/"요금제"/"작업큐"/"업종별 관리"/"보관함" 5개 라벨 중 하나를 **텍스트로 검색해 그 DOM을 통째로 복제**해 "회원관리" 항목을 만드는 방식이다. React 사이드바 문구가 바뀌거나 렌더링 타이밍이 어긋나면 다섯 라벨을 전혀 못 찾아 항목 자체가 생성되지 않을 수 있다.
- `v1-admin-member-menu-color.js`가 지정하는 색상은 `#7fffd4`(연한 아쿠아민트 파스텔)로, 사이드바 배경이 밝은 색이면 대비가 매우 낮아 거의 안 보일 수 있다.
- `MutationObserver`가 DOM 변경 시 `createMenu()`를 재시도하므로 단순 타이밍 문제는 자체 복구될 가능성이 있으나, 애초에 5개 라벨이 전혀 없는 경우는 재시도해도 해결되지 않는다.
- 관련 3개 정적 파일 모두 컨테이너 내부에서 HTTP 200으로 정상 서빙되는 것을 확인했다 — 캐시·배포 문제는 아님.

### 4.3 판정

**상태**: SUSPECTED (코드 근거는 확인했으나, 실제 관리자 화면을 브라우저로 열어 최종 확인하지는 못함 — 이번 세션은 브라우저 조작 도구를 사용하지 않았음)

**권장 조치**:
1. 메뉴 생성 방식을 텍스트 라벨 매칭 대신 고정된 DOM 앵커(클래스/데이터 속성)로 전환
2. 색상을 배경과 무관하게 대비가 확보되는 진한 톤 + 배지 배경으로 교체

**모든 항목이 사실과 일치했다.**

### 6.2 재검증 중 확인한 추가 개선사항 (보고에는 없었으나 코드로 확인)

`beta_archive_retention.py`가 291줄에서 486줄로 확장되어 있었다(`2a67c30`, `097f101` 커밋). 전체를 재독한 결과 이전 세션에서 지적했던 미세 지뢰들이 함께 해결되어 있었다.

1. **크래시 중간 상태 복구(`_recover_stale_quarantines_locked`)**: 폴더를 격리 폴더로 옮기는 도중 프로세스가 죽는 경우를 대비해, 매 정리 작업 시작 전에 격리 폴더를 검사한다. DB·압축메타데이터가 둘 다 완료 상태면 마무리 정리하고, DB가 미완료면 원본을 복구하며, 상태가 엇갈리면 **데이터 손실 대신 원본 보존 쪽으로 안전하게 롤백**한다.
2. **프로세스 간 파일 잠금(`fcntl.flock` + `LOCK_FILE`)**: 기존 `threading.Lock`에 더해 파일 잠금이 추가되어, 향후 uvicorn worker가 여러 개로 늘어나도 동시 정리 중복 실행을 막는다(코드 주석에 "future multi-worker processes" 명시).
3. **빈 작업 제외(`_job_has_generated_media`)**: 실제 생성 파일이 없는 작업은 10/20개 계산에서 제외되어, 실패한 빈 작업이 자리만 차지하는 문제가 해결됨.
4. **등급 다운그레이드 지연 반영 문제 해결**: 이전에는 사용자가 새 영상을 만들 때만 정리가 실행됐으나, 이제 1시간 주기 전수 점검이 모든 사용자에 대해 돌기 때문에 유료→무료 하향 시에도 최대 1시간 내 자동 반영된다.
5. **감사 로그 추가(`logs/beta_archive_retention.jsonl`, 5MB 단위 로테이션)**: 정리 실행 내역이 구조화된 JSON 라인으로 기록되어 사후 검증이 가능해짐.

### 6.3 재검증 후 남은 참고사항 (즉시 조치 불필요)

- V1 보관함은 이번 하드닝 대상에서 빠져 있다. 크래시 복구, 프로세스 간 잠금, 감사 로그가 V1에는 없고, 삭제 파일이 `cleanup_trash/`에 무기한 쌓이는 구조 그대로다.
- V1(5단계)·Beta(2단계) 유료 등급 세분화 차이는 이번 하드닝에서도 그대로 남아 있다.
- `archive_limit_for_user()`는 V1 DB에 접근하지 못하면 삭제를 건너뛰도록(fail-safe) 설계되어 있다 — 안전한 설계이나, V1 DB가 일시적으로 막히면 그 사이 정리가 지연될 수 있다(다음 주기에 자동 보정, 데이터 유실 아님).
- 정리 작업 전체가 하나의 잠금으로 순차 처리되므로, 사용자 수가 크게 늘어나 동시에 여러 명이 영상을 완성하는 시점이 잦아지면 정리 처리가 다소 지연될 수 있다(현재 규모에서는 문제 없음).

## 7. 저장 용량 기준 유료회원 수용 가능 인원 산정

### 7.1 근거 데이터 (전부 실측)

- 실제 완료된 Beta 작업(미디어 유지 상태) 22건의 실측 평균 용량: **약 13.6MB/건** (최소 6.9MB ~ 최대 20.5MB, `du -sb` 실측)
- Beta 유료 한도 20건 기준 1인당 필요 용량: 13.6MB × 20 = **약 272MB/명**
- `/home/bourne/StoryMaker_1`가 위치한 디스크(`/dev/nvme0n1p2`): 전체 915GB, 사용 234GB(27%), **여유 635GB**
- 참고: 새벽 자동 백업 대상 `/mnt/lms_ssd`(932GB, `/dev/sda1`)는 물리적으로 별도 디스크로, 이 여유공간과 경쟁하지 않음(`df -h`로 확인)
- 단, 이 635GB는 Beta 전용이 아니라 V2·WordPress·Jellyfin·음악 라이브러리·기타 Docker 서비스·V1 결과물 등 서버의 모든 것이 공유하는 공간이다.

### 7.2 산정 결과

| 가정 | 지원 가능 유료회원 수 |
|---|---|
| 현재 여유공간 635GB 전부를 Beta에 사용 | 약 2,387명 |
| 다른 서비스 성장분 고려, 50%만 여유로 계산 | 약 1,193명 |
| 보수적으로 30%만 여유로 계산 | 약 716명 |
| 매우 보수적으로 10%만 여유로 계산 | 약 238명 |

**결론**: 가장 보수적인 시나리오(10%)에서도 238명까지 지원 가능하며, 저장 공간은 현재 유료회원 확장의 병목이 아니다. 다만 실제 병목 후보는 저장 용량이 아니라 동시 렌더링 처리량·파일 디스크립터(§2, BUG-BETA-005 참고)일 가능성이 크다.
