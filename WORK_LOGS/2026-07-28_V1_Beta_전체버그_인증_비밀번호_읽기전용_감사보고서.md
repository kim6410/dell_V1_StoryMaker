## 2. 실제 인증 경로 지도 (현재 코드 기준 재검증)

### A. 회원가입

```
V1 통합 인증 모달 (auth_modal_unified.js, submitRegister)
  → 사용자명 + 이메일 2개 필드만 입력 (비밀번호 입력란 없음, 2026-07-27 오후 변경)
  → WordPress REST POST /wp-json/storymaker/v1/register (username, email만 전송)
  → Hostinger storymaker-auth 플러그인 v1.1.0 (V1 저장소 밖, Hostinger 서버 소재 — 이번 조사에서 재열람하지 않고 07-27 업무일지 내용을 인용)
    → register_new_user() 실행 → wp_users 사용자 즉시 생성
    → 신규 가입자에게만 storymaker_email_verified=0 메타 부여 (기존 회원은 메타 없음 = 인증완료 간주)
    → WordPress 코어가 "비밀번호 설정" 메일 발송 (wp_mail 성공=수신 보장 아님)
    → 메일 링크 클릭 → 비밀번호 설정 완료 → after_password_reset 훅에서 storymaker_email_verified=1
  → V1 로컬 DB 사용자 생성 시점: 회원가입 시점이 아니라 "첫 로그인 성공 시점" (auth.py:540-577)
    → WordPress 로그인 성공 후 wordpress_user_id로 조회, 없으면 신규 User row 생성
    → 로컬 password_hash에는 req.password가 아니라 hash_password(secrets.token_urlsafe(32)) 랜덤값 저장 (auth.py:557)
```
**V1 자체 회원가입 API(`POST /auth/join`, auth.py:661-669)는 항상 HTTP 400을 반환하도록 차단되어 있음을 현재 코드로 재확인**. 즉 V1 DB에 직접 가입하는 경로는 없다 — WordPress가 유일한 회원 원장.

### B. 로그인

```
V1 로그인 모달 → POST /v1-api/auth/login (WindowsV1ApiCompatMiddleware가 /api로 rewrite)
  → auth.py:475 login()
  → guest/guest 하드코딩 예외 (별도 §3-2)
  → 일반 계정: httpx로 Hostinger POST /wp-json/storymaker/v1/login 호출
  → WordPress 인증 성공(200) → wordpress_user_id로 V1 로컬 사용자 조회/생성, role 동기화(administrator→admin)
  → WordPress 인증 실패(≠200) → HTTP 400 "아이디 또는 비밀번호가 일치하지 않습니다" (이메일 미인증 403도 이 문구로 뭉뚱그려짐, §3-9)
  → WordPress 통신 장애 → HTTP 502
  → 성공 시 UserSession 신규 행 생성 + JWT 발급(sub, username, role, session_id 포함) + storymaker_token HTTP-only 쿠키 설정(SameSite=Lax, 7일)
  → localStorage에는 access_token을 응답 바디로도 함께 반환(TokenResponse) — 프런트가 localStorage에 저장하는지는 프런트 코드별로 다름(아래 §3 참고, 전수 확인 못함)
```
Beta로 전달되는 서명 헤더는 로그인 시점에는 발급되지 않는다. V1→Beta 프록시가 요청마다 `X-Storymaker-User-Id`, `X-Storymaker-User-Role`, `X-Storymaker-Auth-Time`, `X-Storymaker-Auth-Signature`(HMAC-SHA256, `BETA_INTERNAL_AUTH_SECRET` 사용, 300초 유효)를 동적으로 생성해 요청마다 첨부한다(main.py:2184-2194, StoryMaker_beta/app/beta_auth.py).

### C. 비밀번호 찾기·재설정

```
V1 모달 "비밀번호 찾기" → POST /v1-api/auth/password-reset-request {login}
  → auth.py:676 request_password_reset()
  → Rate Limit: IP 3회/15분 + 계정(SHA-256 해시) 3회/15분
  → httpx GET 후 POST https://mystorymaker.net/wp-login.php?action=lostpassword (follow_redirects=False)
  → 본문에 하드코딩된 3개 실패 문자열("이메일을 보낼 수 없습니다","The email could not be sent","wp_mail_failed") 또는 5xx가 있으면 502, 그 외에는 항상 동일한 성공 문구 반환
  → 실제 새 비밀번호 확정은 V1이 아니라 WordPress 코어 화면(메일 링크)에서 전부 처리됨 — V1에는 "재설정 확정" API 자체가 없음
```
**여기서 확정된 새 비밀번호는 WordPress 원장에 직접 반영되므로, "비밀번호 찾기"로 바꾼 비밀번호는 다음 로그인에 실제로 반영된다.**

### D. 마이페이지 비밀번호 변경 — 최우선 확인 대상

```
PUT /v1-api/auth/change-password {current_password, new_password}
  → auth.py:735 change_password()
  → verify_password(current_password, current_user.password_hash) 로 "현재 비밀번호" 검증
  → current_user.password_hash = hash_password(new_password)  ← V1 로컬 DB 컬럼만 변경
  → WordPress에는 어떤 요청도 전송하지 않음
  → 응답: "비밀번호가 안전하게 변경되었습니다. 다시 로그인해 주세요."
```
**§3-1에서 CONFIRMED로 상세 기술.**

### E. 로그아웃

```
프런트 로그아웃 함수 → POST /v1-api/auth/logout
  → auth.py:776 logout()
  → Authorization 헤더 없으면 storymaker_token 쿠키에서 JWT 추출(2026-07-27 보강분, 재검증 결과: 유지됨)
  → payload의 session_id로 UserSession.logout_at, duration_seconds 기록
  → _clear_auth_cookie()로 쿠키 삭제
  → 로그아웃 후 같은 JWT 재사용 시: get_current_user()가 session_id로 DB를 조회해 logout_at이 채워져 있으면 401 (재검증 결과: 유지됨, session_id 없는 구형 토큰은 무조건 401)
```
다른 탭·다른 서브도메인: 쿠키 Domain이 `.mystorymaker.net`으로 설정되어 `mystorymaker.net`과 그 하위 모든 서브도메인에 공유된다(auth.py:45, 142-150). 로그아웃은 이 쿠키 자체를 지우므로 같은 브라우저의 다른 탭에서도 쿠키가 사라지지만, **localStorage에 access_token을 별도로 저장해둔 다른 탭이 있다면 그 탭은 로그아웃 API를 다시 호출하기 전까지 Authorization 헤더로 계속 인증될 수 있다**(JWT 자체는 만료 전까지 유효하고, 로그아웃 처리는 DB 세션 기준이므로 로그아웃 이후에는 401이 되어야 정상 — 이 부분은 실제로 로그아웃 API가 호출되어야만 세션이 무효화되므로, "쿠키만 지우고 로그아웃 API를 호출하지 않는" 프런트 코드 경로가 있다면 위험. 이번 조사에서 모든 프런트 로그아웃 호출부를 전수 검사하지는 못해 **SUSPECTED**로 남긴다).

### F. Beta 인증

```
V1 로그인 사용자 → V1 /v1/beta-api/* 프록시(main.py:2282) → 요청마다 HMAC 서명 헤더 첨부 → Beta(8021) 미들웨어 enforce_beta_user_isolation
  → /beta-api로 시작하지 않는 경로는 서명 검사 생략(정적 파일, /beta, /beta/production, /beta/archive HTML)
  → /beta-api/*는 require_signed_user()로 서명·시각창(300초)·HMAC 검증
  → URL에 /jobs/{beta_job_id}가 포함되면 require_job_owner()로 DB owner_user_id와 서명된 user_id 대조, 불일치 시 404(타 사용자 존재 여부 비노출)
  → 관리자 역할은 owner_user_id가 NULL인 고아 작업에만 예외 접근 가능 — 실제로는 "관리자가 모든 작업에 접근 가능"이 아니라 오히려 소유자 있는 작업엔 관리자도 404 (§3-14, 과도한 우회가 아니라 반대로 지나치게 좁음)
```
**직접 8021 접근 시 인증 우회 가능성**: `storymaker-beta.service`가 `0.0.0.0:8021`로 직접 리슨 중임을 `ss -ltnp`로 확인했다(방화벽·프록시 레벨 필터링 여부는 이번 조사 범위 밖 — UNKNOWN). 그러나 8021에 직접 접속해도 `/beta-api/*`는 여전히 `BETA_INTERNAL_AUTH_SECRET` 기반 HMAC 서명이 필요하므로, 이 시크릿을 모르는 외부 요청은 401로 차단된다(코드 확인, CONFIRMED). 다만 `/beta`, `/beta/production`, `/beta/archive`, `/beta-static/*`(정적 자산)는 서명 없이 그대로 열람 가능 — 이는 페이지/정적 자산 노출이지 데이터 접근은 아니므로 낮은 위험으로 분류.

## 3. 발견 사항 목록

### [BUG-AUTH-001] 마이페이지 비밀번호 변경이 "성공" 표시와 달리 실제 로그인 비밀번호(WordPress)를 변경하지 않음

- **위험도**: HIGH
- **상태**: CONFIRMED (코드 직독으로 100% 확정, 실행 재현은 하지 않음 — 실제 비밀번호 변경 자체가 금지 행위이므로)
- **영향**: 사용자가 "비밀번호가 안전하게 변경되었습니다"라는 성공 메시지를 보고 안심하지만, 실제 로그인 시 검증되는 WordPress 비밀번호는 그대로다. 계정 탈취 의심 후 비밀번호를 바꿨다고 믿는 사용자가 실제로는 전혀 보호되지 않는 상태로 남는다.
- **재현 조건**: 로그인한 사용자가 마이페이지에서 "비밀번호 변경"을 시도하면 항상 발생(조건 없음, 100% 재현).
- **현재 동작**: `PUT /v1-api/auth/change-password`(`auth.py:735-773`)가 `current_user.password_hash`(V1 로컬 DB 컬럼)만 Argon2id로 갱신하고 종료. WordPress로 어떤 API 호출도 하지 않는다. 반면 일반 로그인(`auth.py:502-579`)은 오직 WordPress `/wp-json/storymaker/v1/login` 응답만으로 인증하며 로컬 `password_hash`를 전혀 참조하지 않는다. 게다가 WordPress 연동으로 새로 생성되는 사용자의 로컬 `password_hash`는 애초에 `hash_password(secrets.token_urlsafe(32))`(`auth.py:557`, `auth.py:632`)라는 **사용자가 알 수 없는 무작위 값**이다.
- **정상 동작**: "비밀번호 변경"은 실제 로그인 원장(WordPress)에 반영되어야 하며, 반영되지 않는 값을 바꾸고 성공 메시지를 표시해서는 안 된다.
- **근거 파일**: `storymaker-web/backend/app/api/auth.py`
- **근거 함수·라인**: `change_password()` 735-773행, `login()` 540-577행(로컬 해시 미참조), 557행·632행(랜덤 로컬 해시 생성)
- **관련 DB**: `storymaker.db.users.password_hash` — 이번 조사에서 6명 중 3명이 Argon2id, 3명이 레거시 SHA-256 64자리 해시로 확인(값은 미열람, 형식만 확인).
- **관련 로그**: 해당 없음(기능 로직 결함, 오류 로그로는 드러나지 않음)
- **사용자에게 보이는 현상**: "비밀번호가 안전하게 변경되었습니다. 다시 로그인해 주세요." 성공 토스트가 뜨고, 실제로 재로그인 시 새 비밀번호가 아니라 기존 WordPress 비밀번호로만 로그인된다. 사용자는 자신이 입력한 "새 비밀번호"로 로그인이 실패하는 이유를 알 수 없다.

```
가입 요청(테스트 계정)
→ 인증 메일 수신 확인
→ 링크 1회 사용 확인(재사용 시 거부되는지)
→ 비밀번호 설정
→ 첫 로그인
→ 업체정보 등록
→ Beta 접근 및 usage-summary 확인(수정 전: 20/20으로 보이는지 재확인)
→ 비밀번호 찾기
→ 새 비밀번호 설정
→ 이전 비밀번호로 로그인 실패 확인
→ 새 비밀번호로 로그인 성공 확인
→ 기존 세션(다른 브라우저)이 여전히 유효한지 확인 → BUG-SESS 관련 개선 여부 검증
→ 로그아웃 후 같은 JWT 재사용 시 401 확인
→ 무료 사용량 중복 차감 확인: 동일 테스트 계정으로 두 작업을 거의 동시에 렌더링 요청해 한도가 정확히 20에서 끊기는지 확인(BUG-BETA-003 수정 검증)
```

## 8. 조사 중 확인한 선행 보고서 항목의 현재 상태 재검증 요약

| 선행 보고서 항목 | 현재 상태 |
|---|---|
| CRIT-1 JWT 키 하드코딩 | **해결 유지 확인**. `settings.py` 기본값 공란, `docker-compose.yml`이 `${STORYMAKER_JWT_SECRET}` 참조로 전환됨. `session_id` 없는 토큰은 `get_current_user`가 즉시 거부(코드 확인). |
| CRIT-2 SHA-256 고정 salt | **부분 해결**. 신규 저장은 Argon2id(`security.py` 확인). 레거시 사용자 3명은 여전히 SHA-256(검증만 허용, 신규 저장 없음). |
| CRIT-3 `/data/output_results` 무인증 | **해결 유지 확인**. 현재 `get_current_user` 의존성 + 소유권 검사(403) 존재(`main.py:1971-1998`). |
| CRIT-4 취약한 기본 관리자 시딩 | **해결 유지 확인 (재검증)**. `settings.py`의 `STORYMAKER_ADMIN_USER/PASSWORD` 기본값 공란. 07-27 업무일지 기준 시딩 시 16자 미만 비밀번호 거부 로직 추가 주장 — 이번 세션에서 `repositories.py` 해당 함수 재열람은 하지 않아 **SUSPECTED로 유지**. |
| CONF-5 `/static` 백업파일 노출 | 이번 세션에서 재요청(curl) 테스트는 하지 않음 — **UNKNOWN, 재확인 필요**. |
| CITED-1 이메일 인증 미검증 | **부분 개선**. WordPress 플러그인 v1.1.0이 신규 가입자 대상 `storymaker_email_verified=0`/403 체계를 도입했다고 07-27 업무일지에 기록됨(V1 저장소 밖 코드라 이번 세션에서 직접 재열람 못함, **CITED로 유지**). V1 로그인 코드가 이 403을 구분 없이 처리하는 문제는 BUG-AUTH-009로 별도 기록. |
| CITED-2 비밀번호 원장 이원화 | **미해결, 재확정**. 이번 조사의 BUG-AUTH-001로 재확정. 사용자가 우려한 모순이 현재 코드에도 그대로 존재함. |
| CITED-3 WordPress 사용자 목록 401 | **UNKNOWN, 재확인 필요**. 이번 세션에서 실제 WordPress REST 재호출로 재검증하지 않음. |
| Rate Limit 부재(CONF-6) | **해결 유지 확인**. 로그인 5회/5분, 비밀번호 찾기 3회/15분 IP+계정 기준 적용 확인(`auth.py`). 회원가입(WordPress REST) 자체에는 V1 레벨 Rate Limit 없음. |
| 쿠키 도메인 전역 공유(CONF-7) | **미해결, 유지 확인**. `.mystorymaker.net` 그대로. |
| 세션 소유권 교차검증 누락 | 07-27 마지막 업무일지가 "다음 작업 1순위"로 남긴 `get_current_user`/`get_optional_current_user`의 `session_rec.user_id == user.id` 교차검증 — 이번 세션 코드 재확인 결과 **여전히 이 교차검증 코드는 없음**(session_id로 세션을 찾은 뒤 그 세션이 속한 user_id와 JWT의 `sub`/`username`이 일치하는지 별도로 비교하는 코드가 `auth.py:280-306`에 없음). JWT 서명 키를 모르면 위조가 불가능하므로 실질 악용 난이도는 높으나, **미해결 상태로 재확정(SUSPECTED, 실제 악용 재현은 하지 않음)**. |

## 9. 이번 조사에서 다루지 못한 항목 (UNKNOWN — 후속 조사 필요)

- 사용자 요청 체크리스트 중 아래 항목은 코드 근거가 간접적이거나, 실제 HTTP 요청 재현이 필요해 이번 읽기 전용 조사에서 확정하지 못했다. 추측으로 단정하지 않고 명시적으로 UNKNOWN 처리한다.
  - `/static` 백업 파일의 외부(운영 도메인) 노출 여부 재확인
  - WordPress 사용자 목록 401의 현재 상태
  - `seed_admin_user`의 16자 비밀번호 강제 로직 현재 코드 재열람
  - Hostinger `storymaker-auth` 플러그인 v1.1.0의 실제 코드(V1 저장소 밖)
  - Nginx Proxy Manager/Caddy 레벨에서 8021 포트 외부 노출 여부(방화벽 룰)
  - 프런트엔드 localStorage 토큰 저장 여부의 전체 코드 경로(모든 JS 파일 전수 검사는 하지 않음)
  - V1 401 응답 18,094건(24시간)의 원인 성격(정상 폴링 vs 이상 트래픽) — 통계만 확인, 원인 미분석
  - 관리자 화면 실제 브라우저 렌더링 결과(모든 조사는 코드·DB·로그 기반, 브라우저 조작은 수행하지 않음)
