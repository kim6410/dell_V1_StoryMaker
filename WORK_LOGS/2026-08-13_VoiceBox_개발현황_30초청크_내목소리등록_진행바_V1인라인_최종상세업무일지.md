# 3. systemd 자동기동 상태

VoiceBox는 현재 임시 수동 프로세스가 아니라 systemd 서비스로 등록되어 있다.

서비스명:

```text
storymaker-v1-voicebox.service
```

현재 확인 결과:

```text
systemctl is-enabled storymaker-v1-voicebox.service
→ enabled

systemctl is-active storymaker-v1-voicebox.service
→ active
```

실제 실행 명령:

```text
/home/bourne/StoryMaker_1/voicebox/runtime/venv/bin/python
-m backend.main
--host 0.0.0.0
--port 17493
--data-dir /home/bourne/StoryMaker_1/voicebox/runtime/data
```

VoiceBox 데이터베이스 경로:

```text
/home/bourne/StoryMaker_1/voicebox/runtime/data/voicebox.db
```

초기에는 `uvicorn backend.main:app`을 직접 실행해 기본 `voicebox/data`를 참조하면서 SQLite readonly 문제가 있었다.

해결 방식:

```text
python -m backend.main --data-dir <runtime/data>
```

공식 진입점을 사용하도록 systemd ExecStart를 변경했다.

현재 DB readonly 경고는 해결된 상태다.

# 4. VoiceBox Health 상태

현재 Dell 호스트에서 직접 확인한 VoiceBox `/health` 결과 핵심은 다음과 같다.

```json
{
  "status": "healthy",
  "gpu_available": true,
  "gpu_type": "CUDA (NVIDIA GeForce GTX 1060 with Max-Q Design)",
  "backend_type": "pytorch",
  "backend_variant": "cuda"
}
```

VoiceBox 서버는 현재 포트 `17493`에서 동작한다.

```text
0.0.0.0:17493
```

단, 외부 전체 공개 상태가 아니다.

UFW 규칙:

```text
17493/tcp ALLOW 172.27.0.0/16
```

기본 inbound 정책은 deny다.

따라서 현재 17493은 V1 Docker 내부 네트워크에서만 접근할 수 있도록 제한돼 있다.

model_name: qwen-tts-0.6B

# 7. GPU VRAM 관리 문제와 해결 방향

Qwen Base 0.6B와 Qwen CustomVoice 0.6B 두 모델을 동시에 GPU에 올렸을 때 GTX1060 6GB VRAM이 거의 가득 찼다.

실측 최대 사용:

```text
약 5.84GB
```

이 상태에서 긴 음성 생성을 시작하면 OOM 위험이 높다.

따라서 Adapter에 선택 모델 기반 unload 전략을 추가했다.

예상 흐름:

```text
Sohee 생성 요청
→ qwen-tts-0.6B GPU unload
→ qwen-custom-voice-0.6B 필요 시 load
→ 생성
```

내 목소리 생성 요청:

```text
내 목소리 Profile 선택
→ qwen-custom-voice-0.6B GPU unload
→ qwen-tts-0.6B 필요 시 load
→ 생성
```

주의:

이 작업은 모델 파일을 삭제하지 않는다.

```text
디스크 캐시 유지
GPU 메모리에서만 unload/load
```

따라서 다시 HuggingFace에서 2.4GB를 다운로드할 필요가 없다.

# 9. VoiceBox V1 Adapter API

현재 V1 Backend OpenAPI에서 확인되는 VoiceBox 경로는 다음과 같다.

```text
/api/voicebox/health
/api/voicebox/profiles
/api/voicebox/profiles/clone
/api/voicebox/generate/chunk
/api/voicebox/generate/start
/api/voicebox/generate/{generation_id}/status
/api/voicebox/generate/{generation_id}/audio
```

실제 외부 V1 prefix에서는 `/v1-api/voicebox/...` 형태로 사용한다.

## 9.1 Health

```text
GET /v1-api/voicebox/health
```

역할:

```text
V1 Backend
→ VoiceBox 17493 /health
→ online 상태 반환
```

## 9.2 Profiles

```text
GET /v1-api/voicebox/profiles
```

VoiceBox DB에 저장된 음성 프로필 목록을 Studio UI로 전달한다.

## 9.3 Voice Clone

```text
POST /v1-api/voicebox/profiles/clone
```

목표 입력:

```text
profile_name
reference_text
engine
sample audio file
```

처리 순서:

```text
1. VoiceBox /profiles로 cloned profile 생성
2. /profiles/{profile_id}/samples로 음성 파일 업로드
3. reference_text 저장
4. Studio Voice Profile select 목록 새로고침
```

## 9.4 비동기 Generation

```text
POST /v1-api/voicebox/generate/start
```

VoiceBox `/generate`를 호출해 generation ID를 발급받는다.

상태:

```text
loading_model
generating
completed
failed
```

## 9.5 Status

```text
GET /v1-api/voicebox/generate/{generation_id}/status
```

VoiceBox `/history/{generation_id}`를 조회한다.

## 9.6 Audio

```text
GET /v1-api/voicebox/generate/{generation_id}/audio
```

완료된 WAV를 브라우저로 stream한다.

# 10. 실제 Progress UI/UX

사용자 요구사항:

```text
음성 생성 중 현재 어디까지 진행됐는지 눈으로 확인 가능해야 한다.
```

초기 방식은 `/generate/stream` 한 요청을 30~60초 동안 붙잡는 구조라 브라우저가 내부 단계를 알 수 없었다.

이를 generation ID 기반 비동기 방식으로 변경했다.

현재 Studio 진행 단계:

```text
[모델 준비]
     ↓
[음성 생성]
     ↓
[오디오 수신]
     ↓
[완료]
```

VoiceBox가 내부 추론의 정확한 0~100% 값을 제공하지 않는 구간에서는 가짜 퍼센트를 만들어내지 않는다.

대신:

```text
움직이는 indeterminate progress bar
실제 경과시간
실제 VoiceBox status
```

를 보여준다.

오디오 응답 다운로드가 시작되면:

```text
received bytes / content-length
```

를 사용하여 실제 전송 퍼센트를 계산한다.

예:

```text
오디오 수신 62%
218 KB / 351 KB
```

완료되면:

```text
100%
완료
실제 재생시간 표시
```

로 변경한다.

# 12. 30초 청크 생성 예상시간

Dell GTX1060 + Qwen 0.6B 기준 현재 예상치는 다음과 같다.

## Warm 상태

이미 해당 모델이 GPU에 올라가 있는 경우:

```text
약 25~45초 / 30초 음성 청크
```

## Cold 상태

다른 TTS 모델을 사용하다 모델 전환이 필요한 경우:

```text
모델 unload
→ 새 모델 load
→ 생성
```

예상:

```text
약 40~70초 / 30초 음성 청크
```

현재 짧은 실측에서 5.28초 음원을 Cold 상태로 생성했을 때 총 29.8초가 소요됐다.

다만 TTS 생성시간은 출력 음성 길이에 완전히 선형 비례하지 않는다.

따라서 30초 청크 예상값은 현재까지의 GPU/모델 실측을 바탕으로 한 운영 예상치다.

향후 2분 테스트 대본을 실제 4개 청크로 생성하여 다음 표를 자동 기록하면 더 정확한 ETA를 만들 수 있다.

```text
Chunk 01 / text chars / audio duration / model load / generation / download / total
Chunk 02 / ...
Chunk 03 / ...
Chunk 04 / ...
```

이 데이터를 20~50개 정도 누적하면 UI에서 다음과 같은 예상시간을 표시할 수 있다.

```text
현재 청크 예상 완료: 약 32초 후
전체 4개 예상 완료: 약 2분 18초 후
```

# 13. Smart Chunker 구조

전체 긴 대본을 한 번에 TTS로 보내지 않는다.

지원 목표:

```text
20초
30초 기본
40초
```

한국어 분할 기준:

```text
.
?
!
줄바꿈
문장 길이
예상 발화시간
```

30초를 정확한 초 단위로 자르는 것이 아니라 문장이 자연스럽게 끝나는 지점을 우선한다.

목표:

```text
약 20~40초 범위
```

청크 객체 예시:

```javascript
{
  id: 'chunk-...',
  text: '...',
  status: 'DRAFT',
  versions: [],
  selectedVersion: null,
  error: '',
  progress: {
    phase: 'idle',
    label: '대기',
    startedAt: 0,
    bytesReceived: 0,
    totalBytes: 0,
    percent: null
  }
}
```

# 14. 청크별 생성/재생성/버전 선택

현재 설계된 핵심 워크플로우:

```text
전체 대본 입력
→ 30초 자동 분할
→ Chunk #01 생성
→ 재생
→ 마음에 안 들면 재생성
→ V1 / V2 / V3 비교
→ 최종 버전 선택
→ 다음 청크
```

각 청크는 독립적이다.

따라서 긴 대본 중 한 문장의 발음이 이상하더라도 전체 5분 음성을 처음부터 다시 만들 필요가 없다.

버전 객체 예시:

```javascript
{
  id: 'v-...',
  label: 'V2',
  url: blobUrl,
  blob: wavBlob,
  durationSec: 28.4,
  createdAt: '...'
}
```

# 18. 최종 Export 설계

모든 청크에서 최종 버전이 하나씩 선택되면 다음 작업을 한다.

```text

선택된 WAV 02
선택된 WAV 03
...
```

청크 사이 기본 무음:

```text
300ms
```

최종 결과:

```text
project_final.wav
project_final.mp3
project_final.srt
```

필요 시:

```text
project_chunks.zip
project_final.vtt
project_final.json
```

까지 확장 가능하다.

SRT는 글자 수 추정으로 만들지 않는다.

반드시 최종 선택된 WAV의 실제 duration을 읽어서 다음 청크 시작 시간을 계산해야 한다.

예시:

```text
Chunk1 duration = 28.42 sec
padding = 0.30 sec
Chunk2 start = 28.72 sec
```

이 방식을 사용하면 영상 뒤쪽으로 갈수록 자막이 밀리는 문제를 최소화할 수 있다.

# 20. Supertonic 보호 원칙

VoiceBox는 기존 Supertonic을 교체하는 것이 아니다.

StoryMaker Voice Engine 구조 목표:

```text
1. Supertonic
   기존 안정 기본음성

2. VoiceBox
   고급 한국어 / 음성복제 / 감정 / 여러 TTS 엔진

3. Browser TTS
   향후 WebGPU/WASM 경량음성
```

따라서 VoiceBox 개발 중 다음은 건드리지 않는다.

```text

기존 V1 production pipeline
기존 DB schema
기존 Worker
기존 영상 생성 파이프라인
```

VoiceBox는 별도 Adapter를 통해 선택형 엔진으로 추가한다.

# 28. 2026-08-13 추가 구현 — 전체 청크 자동 순차 생성

사용자 요청에 따라 개별 청크마다 생성 버튼을 반복해서 누르지 않아도 되도록 전체 자동 순차 생성 기능을 추가했다.

상단 툴바와 최종 하단 패널에 모두 아래 버튼을 제공한다.

```text
전체 청크 순차 생성
```

동작 규칙은 다음과 같다.

```text
1. 전체 대본을 Smart Chunker로 20/30/40초 기준 분할
2. Voice Profile 선택 여부 확인
3. VoiceBox 엔진 online 여부 확인
4. Chunk #1이 미완료이면 생성 시작
5. /generate/start에서 generation_id 수신
6. /generate/{id}/status를 700ms 주기로 실제 폴링
7. loading_model → generating → completed 상태 감지
8. completed 후 /audio로 WAV를 브라우저에 수신
9. 선택 버전이 정상 생성됐는지 확인
10. 정상 완료된 경우에만 Chunk #2 시작
11. 같은 방식으로 마지막 청크까지 순차 처리
12. 이미 선택된 최종 버전이 있는 청크는 자동 건너뜀
13. 중간 청크에서 ERROR 발생 시 그 자리에서 전체 순차 작업 중지
14. 사용자가 오류 청크를 수정한 뒤 다시 전체 순차 생성을 누르면 완료된 청크는 건너뛰고 이어서 진행
```

이 구조는 GTX1060 6GB에서 GPU TTS를 병렬 실행하지 않는다는 기존 안전 원칙을 유지한다.

여러 청크를 동시에 GPU에 넣지 않으며 반드시 1개씩 직렬 처리한다.

UI에는 전체 진행률도 추가했다.

```text
0 / 4
1 / 4
2 / 4
3 / 4
4 / 4
```

청크 완료 개수를 기준으로 전체 진행바가 실제 0~100%로 증가한다.

개별 청크 진행바는 기존과 동일하게 실제 VoiceBox generation 상태를 표시한다.

```text
모델 준비
→ 음성 생성

→ 완료
```

# 29. 최종 하단 패널 — 최종 WAV 합치기·자동저장

사용자 요청에 따라 모든 청크 아래쪽에 별도 `FINAL EXPORT` 패널을 추가했다.

최종 패널에는 다음 요소가 있다.

```text
전체 청크 생성 진행상태
완료 청크 수 / 전체 청크 수
전체 진행바
전체 청크 순차 생성 버튼
최종 WAV 합치기·자동저장 버튼
```

`최종 WAV 합치기·자동저장` 버튼은 모든 청크에 선택된 최종 버전이 존재할 때만 활성화된다.

병합은 WAV 파일 바이트를 단순 이어붙이지 않는다.

브라우저의 AudioContext를 사용해 각 청크 WAV를 실제 PCM 오디오로 디코딩한 후 하나의 새로운 PCM 스트림으로 합친다.

병합 순서:

```text
Chunk #1 선택 버전
→ 설정된 무음
→ Chunk #2 선택 버전
→ 설정된 무음
→ Chunk #3 선택 버전
→ ...
→ 최종 WAV 인코딩
```

청크 간 무음 설정은 기존 UI 값을 그대로 사용한다.

```text
0.1초
0.3초 기본
0.5초
0.8초
```

AudioContext는 24kHz 기준으로 생성하며 각 청크를 동일 컨텍스트에서 디코딩해 샘플레이트를 통일한다.

최종 WAV는 PCM 16bit RIFF/WAVE 형식으로 다시 인코딩한다.

파일명 규칙:

```text
{프로젝트명}_최종나레이션.wav
```

프로젝트명에 파일명으로 사용할 수 없는 문자가 있으면 `_`로 안전 치환한다.

병합 완료 후 브라우저에서 별도의 추가 확인 버튼 없이 자동 다운로드를 시작한다.

즉 사용자가 요청한 흐름은 다음과 같다.

```text
전체 청크 순차 생성
→ 모든 청크 완료 감지
→ 최종 WAV 합치기 버튼 활성화
→ 버튼 클릭
→ PCM 병합
→ WAV 생성
→ 자동 저장
```

# 30. V1 인라인 통합 최종 구조

VoiceBox 관리자 진입은 새 페이지로 이동하지 않는다.

기존 V1의 `v1-dashboard-inline-labs.js` 공통 인라인 앱 구조에 VoiceBox를 세 번째 앱으로 등록했다.

```text
AI 연구실
네모트론 연구실
VoiceBox
대시보드로 돌아가기
```

관리자 VoiceBox 플로팅 버튼 클릭 시 `window.location.href`를 사용하지 않고 다음 CustomEvent를 발생시킨다.

```text
storymaker-open-inline-lab
```

`type=voicebox`를 받아 기존 V1 대시보드 콘텐츠 안에 VoiceBox iframe을 표시한다.

VoiceBox iframe 내부의 자체 `V1 대시보드` 버튼은 인라인 모드에서 숨겨 중복 내비게이션을 제거한다.
