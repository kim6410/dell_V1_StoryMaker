# Claude 독립형 StoryMaker 웹앱 단계별 개발 명세서

- 문서 목적: 기존 StoryMaker 소스코드를 전혀 참고하지 않고, 5800X Windows PC에서 독립 실행되는 새로운 StoryMaker 웹앱을 처음부터 설계·구현한다.
- 개발 대상 이름: `StoryMaker Claude Lab`
- 개발 방식: 기능을 한꺼번에 만들지 않는다. 먼저 화면 껍데기와 전체 사용자 흐름을 보여주고 사용자 승인을 받은 뒤, 단계별로 실제 기능을 연결한다.
- 최우선 평가 항목: 개발 속도보다 구조적 안정성, 데이터 격리, 복구 가능성, 사용자 경험, 검증 기록.

---

## 1. 절대 원칙

1. 기존 StoryMaker V1, Beta, Dell 서버 코드를 열거나 복사하거나 참고하지 않는다.
2. 기존 DB 스키마, 함수명, API 경로, JavaScript 번들, CSS, 프롬프트 파일을 답안처럼 사용하지 않는다.
3. 기능 요구사항만 보고 새로운 구조로 직접 설계한다.
4. 기존 운영 서비스, 포트, DB, 작업 폴더, 환경변수, 미디어 폴더와 연결하지 않는다.
5. 5800X 전용 프로젝트 루트, 가상환경, DB, 로그, 작업 폴더, 백업 폴더를 사용한다.
6. 기존 StoryMaker 관련 파일을 수정·삭제·이동하지 않는다.
7. 전체 덮어쓰기, 무분별한 자동 수정, 대규모 일괄 치환을 금지한다.
8. 모든 기능은 사용자별 데이터가 섞이지 않도록 설계한다.
9. API 키, 비밀번호, 실제 회원 개인정보는 코드와 Git에 저장하지 않는다.
10. 사용자가 승인하기 전에는 다음 개발 단계로 넘어가지 않는다.
11. 사용자가 승인하기 전에는 Git 커밋과 Push를 하지 않는다.
12. 개발 중 오류가 발생해도 임시 우회로 숨기지 말고 원인과 해결 내용을 기록한다.

## 2. 권장 독립 실행 환경

아래 값은 충돌이 없도록 시작점으로 사용하되, 5800X 환경을 점검한 뒤 확정한다.

```text
프로젝트 루트: F:\StoryMaker_Claude_Lab
앱 코드: F:\StoryMaker_Claude_Lab\app
DB: F:\StoryMaker_Claude_Lab\data\storymaker_claude.db
작업 폴더: F:\StoryMaker_Claude_Lab\data\jobs
공용 이미지: F:\StoryMaker_Claude_Lab\data\media\images
로그: F:\StoryMaker_Claude_Lab\logs
백업: F:\StoryMaker_Claude_Lab\backups
Python 가상환경: F:\StoryMaker_Claude_Lab\.venv
접속 주소: http://127.0.0.1:8031
```

필수 조건:

- Windows 재부팅 후에도 수동으로 쉽게 다시 실행할 수 있어야 한다.
- 기존 8011, 8021, 7788, 7789 등 운영 포트와 충돌하지 않아야 한다.
- SQLite를 기본 DB로 사용하되, 나중에 PostgreSQL로 옮길 수 있도록 데이터 계층을 분리한다.
- 브라우저는 Chrome 또는 Edge 최신 버전을 기준으로 한다.
- 개발 서버와 운영 실행 명령을 분리한다.

## 3. 기술 선택 원칙

클로드가 기술 스택을 직접 제안하되 아래 조건을 충족해야 한다.

- 백엔드: Python 기반 API 서버 권장.
- 프런트엔드: 반응형 웹 UI. 특정 프레임워크는 자유지만 유지보수가 쉬워야 한다.
- DB: SQLite.
- 인증: 서버 세션 또는 안전한 토큰 방식.
- 비밀번호: 평문 저장 금지. Argon2 또는 동급 해시.
- 미디어 작업: 비동기 작업 상태를 사용자가 확인할 수 있어야 한다.
- 로그: 일반 실행 로그, 오류 로그, 사용자 작업 감사로그 분리.
- 테스트: API, DB, 사용자 격리, 주요 사용자 흐름 자동 테스트.

기술을 선택한 이유와 버전 고정 방식을 첫 업무일지에 기록한다.

## 4. 최종 제품의 사용자 흐름

```text
회원가입 또는 로그인
→ 마이페이지에서 업체 정보 설정
→ 새 콘텐츠 제작 시작
→ 업종·지역·업체 정보·요청사항 입력
→ 대표 이미지 또는 동영상 선택
→ AI 원고 생성
→ SNS 8채널 원고 확인·수정·복사
→ 음성 및 자막 생성
→ 숏폼 MP4 생성
→ 대표 썸네일 8종 미리보기
→ 사용자가 1개 선택 후 저장
→ 보관함 자동 저장
→ 보관함에서 콘텐츠·이미지·음성·자막·MP4·썸네일 확인
```

전체 흐름은 한 화면에서 무리하게 처리하지 말고, 현재 단계와 다음 단계를 명확히 보여준다.

# 개발 단계

## 단계 0. 환경 조사와 프로젝트 생성

목표:

- 5800X의 Windows 버전, Python, Node.js, FFmpeg, GPU, 메모리, 디스크 여유 공간을 확인한다.
- 기존 서비스와 충돌하지 않는 프로젝트 구조와 포트를 확정한다.
- 빈 Git 저장소를 만들되 커밋은 사용자 승인 후 진행한다.

산출물:

- 환경 조사표.
- 최종 디렉터리 구조.
- 실행 명령.
- 선택한 기술 스택과 이유.
- 위험요소 목록.

완료 조건:

- 기존 StoryMaker 파일을 열지 않았음을 명시한다.
- 새 프로젝트 폴더 외에는 아무것도 수정하지 않는다.

## 단계 1. 클릭 가능한 웹앱 껍데기부터 제작

이 단계가 가장 중요하다.

기능을 먼저 구현하지 않는다.

DB, AI API, 음성, MP4 렌더링을 연결하지 않은 상태에서 전체 화면과 클릭 흐름을 먼저 만든다.

사용자가 브라우저에서 직접 확인할 수 있도록 아래 화면을 모두 준비한다.

### 1-1. 공통 레이아웃

- 상단 로고와 서비스명.
- 데스크톱 사이드 메뉴.
- 모바일 하단 또는 햄버거 메뉴.
- 현재 사용자 표시 영역.
- 알림 영역.
- 로딩 상태.
- 오류 메시지.
- 빈 상태 화면.

### 1-2. 화면 목록

1. 랜딩 또는 로그인 화면.
2. 회원가입 화면.
3. 이메일 인증 대기 화면.
4. 비밀번호 찾기 화면.
5. 대시보드.
6. 새 콘텐츠 제작 화면.
7. SNS 8채널 결과 화면.
8. 음성·자막·MP4 제작 화면.
9. 썸네일 선택 화면.
10. 보관함 목록.
11. 보관함 상세.
12. 마이페이지.
13. 구독 및 사용량 화면.
14. 관리자 회원관리 화면.
15. 관리자 요청사항 관리 화면.

### 1-3. 껍데기 제작 규칙

- 실제 동작 대신 명확한 샘플 데이터를 사용한다.
- 버튼을 누르면 다음 화면 또는 모달로 이동해야 한다.
- 제작 단계는 진행 상태가 눈에 보이게 한다.
- 사용자가 어디에 있고 무엇을 해야 하는지 한눈에 보여야 한다.
- 모바일 360px 너비에서도 가로 흔들림이 없어야 한다.
- PC와 모바일 화면을 모두 보여준다.
- 화려함보다 명확한 단계와 쉬운 조작을 우선한다.
- 임시 디자인이어도 실제 서비스처럼 검토할 수 있어야 한다.

### 1-4. 1단계 승인 게이트

클로드는 이 단계가 끝나면 개발을 멈춘다.

다음 내용을 사용자에게 보고한다.

- 접속 주소.
- 구현한 화면 목록.
- 화면별 사용자 흐름.
- 아직 연결하지 않은 기능.
- 사용자가 확인해야 할 항목.

사용자가 화면 구조와 이동 흐름을 승인한 뒤에만 단계 2로 넘어간다.

## 단계 3. 회원가입·로그인·WordPress 연동

목표:

독립 웹앱의 회원 인증을 구현하고, 운영 WordPress 회원과 안전하게 연동할 수 있는 구조를 만든다.

### 3-1. 기본 인증 기능

- 회원가입.
- 이메일 중복 확인.
- 이메일 인증.
- 로그인.
- 로그아웃.
- 비밀번호 찾기.
- 비밀번호 변경.
- 세션 만료.
- 로그인 실패 제한.
- 관리자 권한 검사.

### 3-2. WordPress 연동 원칙

- WordPress는 회원의 기준 계정 시스템으로 사용할 수 있어야 한다.
- WordPress 사용자 ID와 웹앱 사용자 ID를 연결한다.
- WordPress 비밀번호를 웹앱 DB에 복사하지 않는다.
- WordPress REST API 또는 별도 안전한 인증 API를 사용한다.
- Application Password 등 비밀값은 환경변수에만 저장한다.
- WordPress API가 일시적으로 실패할 때 데이터 손실이 없어야 한다.
- 로그인 또는 비밀번호 변경 실패 시 사용자에게 정확한 메시지를 보여준다.
- WordPress에서 구독 상태가 바뀌면 웹앱에 반영할 수 있어야 한다.

### 3-3. 관리자 회원관리

- 전체 회원 목록.
- 이름, 이메일, 업체명, 플랜, 구독기간, 사용량, 최근 활동.
- 회원 상세.
- 계정 활성·비활성.
- 플랜 변경.
- 구독기간 변경.
- 사용량 초기화.
- 관리자 변경 이력 감사로그.

승인 게이트:

- 테스트 계정으로 가입부터 로그아웃까지 브라우저 E2E를 보여준다.
- WordPress 연동 실패 상황과 복구 동작을 보여준다.

## 단계 6. AI 원고 생성 엔진

목표:

업체 정보와 사용자의 요청을 기반으로 SNS 8채널 콘텐츠를 만든다.

### 6-1. 채널 구성

최소 8개 슬롯을 제공한다.

- 네이버 블로그.
- 네이버 플레이스.
- 구글 비즈니스 프로필.
- 인스타그램.
- 페이스북.
- 당근 비즈프로필.
- 카카오채널.
- 숏폼 또는 Reels 설명문.

채널명은 설정 파일로 관리하여 나중에 교체할 수 있게 한다.

### 6-2. 생성 결과

각 채널별로 아래를 저장한다.

- 제목.
- 본문.
- 해시태그.
- 일반 텍스트.

- 생성 시각.
- 사용 모델과 Provider.
- 프롬프트 버전.

### 6-3. AI Provider 구조

- Provider 하나에 종속되지 않는다.
- 우선 Provider 실패 시 다음 Provider로 넘어갈 수 있다.
- API 방식과 브라우저 방식의 결과 저장 구조는 동일해야 한다.
- Provider별 상태와 오류를 로그로 남긴다.
- 비어 있거나 형식이 잘못된 결과는 성공으로 처리하지 않는다.
- 같은 작업을 중복 저장하지 않는다.

### 6-4. 콘텐츠 편집과 복사

- 사용자가 각 슬롯을 직접 수정한다.
- 수정 결과를 즉시 저장하거나 명확한 저장 버튼을 제공한다.
- 채널별 복사 버튼.
- 전체 복사 버튼.
- 네이버 블로그 붙여넣기용 서식 복사.
- 마크다운 기호가 그대로 노출되지 않게 처리한다.
- 모바일에서 긴 글이 읽기 편해야 한다.

승인 게이트:

- 테스트 업체 한 곳으로 8개 슬롯 생성 완주.

## 단계 12. 요금제·사용량·보관 한도

### 월간 제작 한도

- 플랜별 제작 한도는 DB 또는 설정으로 관리한다.
- 관리자 화면에서 조정할 수 있다.
- 사용량 증가 시 중복 집계를 막는다.
- 실패한 작업을 사용량으로 계산할지 정책을 분리한다.

### 보관함 한도

초기 Claude Lab 정책:

- 관리자: 무제한.
- 무료 사용자: 실제 미디어가 있는 최신 10개.
- 유료 사용자: 실제 미디어가 있는 최신 20개.

향후 10/20/50/100/300 등 세분화가 가능하도록 하드코딩하지 않는다.

### 자동정리 원칙

- DB 작업 행과 콘텐츠 기록은 유지한다.
- 초과된 생성 미디어만 정리한다.
- 빈 작업은 보관 개수에 포함하지 않는다.
- 사용자 직접 삭제와 자동정리를 구분한다.
- 정리 이유, 정리 시각, 정리 용량을 기록한다.
- 서비스 시작 시 전체 사용자 점검.
- 미디어 생성 완료 직후 해당 사용자 점검.
- 1시간마다 전체 사용자 점검.
- 등급 변경은 최대 1시간 안에 반영한다.

### 안전한 정리 방식

- 파일을 즉시 삭제하지 않는다.
- 먼저 격리 폴더로 이동한다.
- DB 메타데이터 반영 후 최종 정리한다.
- 중간에 프로세스가 죽으면 다음 시작 시 복구한다.
- DB와 파일 상태가 엇갈리면 데이터 보존 방향으로 롤백한다.
- 스레드 잠금과 프로세스 간 파일 잠금을 함께 사용한다.
- 여러 worker가 동시에 실행되어도 같은 사용자 정리가 중복되지 않아야 한다.
- DB 또는 구독 정보 조회가 실패하면 삭제하지 않는 fail-safe를 적용한다.
- 다음 주기에 자동으로 재시도한다.
- JSONL 감사로그를 남긴다.
- 감사로그는 용량 기준으로 회전한다.

## 단계 18. 사용자 팔로우업 방식

이 프로젝트는 사용자가 개발 과정을 직접 확인하면서 방향을 조정하는 방식으로 진행한다.

클로드는 한 번에 전체 기능을 만들지 않는다.

각 단계는 아래 순서를 지킨다.

```text
1. 이번 단계 목표를 짧게 설명
2. 필요한 파일만 생성 또는 수정
3. 브라우저에서 확인 가능한 결과 준비
4. 사용자에게 접속 주소와 확인 포인트 제공
5. 사용자 피드백 대기
6. 피드백 반영
7. 승인 후 다음 단계 진행
```

특히 첫 번째 결과물은 완성된 백엔드가 아니라 클릭 가능한 웹앱 껍데기여야 한다.

사용자가 메뉴, 배치, 제작 순서, 보관함 구조를 직접 확인하고 수정 방향을 말할 수 있어야 한다.

껍데기 승인을 받기 전에 AI API, WordPress 실제 계정, 음성 엔진, MP4 렌더러 같은 복잡한 기능에 시간을 쓰지 않는다.

사용자에게 장문의 기술 설명만 보여주지 말고 실제 화면과 동작으로 먼저 증명한다.

# 독립 앱 DB 설계 필수 기준

아래 기준은 기존 StoryMaker 코드를 참고하라는 뜻이 아니다.

운영 과정에서 확인된 위험을 새 앱에서 처음부터 피하기 위한 설계 요구사항이다.

## 중앙 SQLite 연결 모듈

모든 SQLite 연결은 단일 연결 모듈을 통한다.

각 기능 파일에서 `sqlite3.connect()`를 개별 호출하지 않는다.

연결 시 아래 정책을 공통 적용한다.

- `journal_mode=WAL`
- `synchronous=NORMAL`
- `foreign_keys=ON`
- `busy_timeout=5000`
- 쓰기 트랜잭션의 명시적 commit·rollback
- 읽기 전용 조회는 URI `mode=ro` 사용

회원 DB나 구독 DB를 조회만 하는 프로세스가 쓰기 가능한 핸들을 열지 않도록 한다.

## DB 파일 이름과 역할 분리

실사용 DB, 테스트 DB, 백업 DB, 폐기 예정 DB는 이름만 보고 구분돼야 한다.

프로젝트 데이터 폴더에 출처가 불명확한 `storymaker.db` 같은 사본을 두지 않는다.

오래된 사본은 운영 데이터 폴더 밖의 백업 위치로 옮기고 파일명에 날짜와 `UNUSED_STALE_COPY`를 표시한다.

앱 시작 시 실제 사용 DB의 절대 경로를 로그에 한 번 기록한다.

## WAL과 무결성 관리

서비스 상태 점검에 아래 항목을 포함한다.

- `PRAGMA integrity_check`
- 현재 journal mode
- WAL 파일 크기
- 최근 `database is locked`, `SQLITE_BUSY`, `disk I/O error`, `malformed` 발생 수

트래픽이 증가하면 `wal_autocheckpoint` 값을 조정할 수 있도록 설정값으로 분리한다.

임의의 주기적 VACUUM은 금지하고, 필요성과 디스크 여유 공간을 확인한 관리 작업으로만 실행한다.

## 백업 기준

백업 스크립트와 최신 백업 마커가 같은 저장 체계를 가리켜야 한다.

문서에 적힌 확인 경로와 실제 최신 백업 경로가 달라지지 않도록 한다.

백업마다 아래 정보를 남긴다.

- 생성 시각
- 대상 DB 절대 경로
- 파일 크기
- SHA-256
- `integrity_check` 결과
- 복원 시험 결과

최신 백업 마커는 백업 성공과 검증 완료 후에만 갱신한다.

## 보관함 정리 확장 기준

초기 구현은 전역 잠금으로 시작할 수 있다.

사용자 증가 시 사용자별 잠금으로 전환할 수 있도록 정리 엔진과 잠금 정책을 분리한다.

보관 한도는 코드에 숫자로 고정하지 않는다.

무료 10개, 유료 20개를 기본값으로 사용하되 향후 10·20·50·100·300 단계가 DB 설정만으로 확장돼야 한다.

등급 DB 조회 실패 시 삭제를 중단하고 다음 주기에 재시도한다.

데이터 유실보다 정리 지연을 선택한다.

DB 단계가 끝나면 장황한 설명 대신 아래 항목만 보고한다.

9. 남은 위험 한 줄
