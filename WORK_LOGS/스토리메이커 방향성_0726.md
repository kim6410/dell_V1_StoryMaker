# StoryMaker 서비스 방향 및 사용자 경험 회의 정리

작성일: 2026-07-26

파일명: `스토리메이커 방향성_0726.md`

---

## 1. 핵심 결론

StoryMaker의 목표는 화려한 AI 기능을 보여주는 것이 아니다.

사용자가 일상과 업무에서 반복하는 복사, 붙여넣기, 키보드 입력, 마우스 이동, 프로그램 전환을 줄여주는 것이 핵심이다.

AI는 전면에 나서는 주인공이 아니라, 사용자의 일을 빠르고 편하게 만들어주는 보조 역할을 맡는다.

StoryMaker의 가치는 다음 문장으로 정리할 수 있다.

> AI는 살짝 거들고, 코드는 반복 작업을 자동화하며, 결과물은 바로 사용할 수 있는 형태로 제공한다.

---

## 2. 실제 사용자 문제

블로그, 인스타그램, 네이버 플레이스, 당근, 유튜브 쇼츠 등 여러 채널에 콘텐츠를 올리는 사람은 다음 작업을 반복한다.

- AI 서비스 창을 열고 프롬프트를 입력한다.
- 채널마다 다른 형식으로 다시 요청한다.
- 결과물을 여러 번 복사하고 붙여넣는다.
- 줄바꿈, 제목, 해시태그, 문장 길이를 다시 수정한다.
- 여러 프로그램과 브라우저 창을 계속 이동한다.
- 작업이 밀리면 여러 콘텐츠를 한꺼번에 처리해야 한다.
- 같은 요청이라도 AI 결과의 품질과 형식이 매번 달라진다.
- 프롬프트를 잘못 입력하면 전체 작업을 다시 해야 한다.

이 과정은 단순해 보이지만 집중력과 시간이 많이 필요하다.

StoryMaker는 이 반복 과정과 불편함을 줄여주는 반자동 업무 도구가 되어야 한다.

---

## 3. 제품 가치 판단 기준

StoryMaker의 가치는 기능 개수나 화면의 화려함으로 판단하지 않는다.

다음 기준을 우선한다.

1. 사용자가 키보드를 덜 입력하게 하는가.
2. 마우스 이동과 클릭 횟수를 줄이는가.
3. 여러 프로그램을 오가는 일을 줄이는가.
4. 복사하고 붙여넣는 작업을 줄이는가.
5. 결과물의 형식과 품질을 일정하게 유지하는가.
6. 생성된 결과를 즉시 게시하거나 활용할 수 있는가.
7. 사용자가 수작업 방식으로 돌아가기 싫다고 느낄 만큼 편리한가.

특히 다음 판단 기준이 중요하다.

> 개발자가 직접 사용했을 때 다시 수작업으로 돌아가기 싫다면, 다른 사용자에게도 충분한 가치가 있을 가능성이 높다.

## 4. 결과물 제공 방식

생성된 콘텐츠는 단순한 AI 답변 형태가 아니라 실제 업무에 바로 사용할 수 있어야 한다.

결과물은 채널별 포맷에 맞춰 제공한다.

예시:

- 네이버 블로그 게시용 원고
- 네이버 플레이스 소식
- 인스타그램 게시물
- 인스타그램 해시태그
- 당근 비즈프로필 게시물
- 유튜브 쇼츠 대본
- 릴스 자막
- 팟캐스트 대본
- 이미지와 영상 제작용 문구
- 복사 버튼으로 즉시 사용할 수 있는 텍스트

사용자는 AI에게 다시 수정 요청을 반복하지 않고, 결과를 복사하여 바로 붙여넣을 수 있어야 한다.

## 5. UI와 사용자 경험 원칙

StoryMaker의 UI는 기능이 많아도 복잡하게 보이지 않아야 한다.

사용자는 내부 구조나 AI 모델을 이해할 필요가 없다.

기본 흐름은 최대한 단순하게 구성한다.

```text
업종 또는 작업 선택
→ 기본 정보 입력
→ 생성 버튼
→ 여러 채널용 결과 자동 생성
→ 복사 또는 파일 저장
```

### UI 원칙

- 버튼 수를 최소화한다.
- 사용자가 다음 행동을 고민하지 않게 한다.
- 주요 기능은 한 화면에서 확인할 수 있게 한다.
- 전문 용어를 줄인다.
- 생성 과정은 자동으로 처리한다.
- 오류가 발생하면 사용자가 이해할 수 있는 문장으로 안내한다.
- 결과물마다 복사와 저장 버튼을 제공한다.
- 모바일과 PC에서 모두 편하게 사용할 수 있게 한다.
- 기능을 숨기기보다 자연스럽게 정리한다.

## 6. 무료 사용자 정책

무료 사용자가 기능 제한 때문에 불편함을 느끼게 해서는 안 된다.

CapCut처럼 사용해볼 만한 기능마다 결제를 요구하면 사용자는 제품의 가치를 충분히 경험하기 전에 피로감을 느낄 수 있다.

StoryMaker는 기능을 막는 방식보다 사용 횟수를 제한하는 방식을 우선한다.

### 기본 원칙

- 무료 사용자도 주요 기능 전체를 사용할 수 있게 한다.
- 기능별 잠금은 최소화한다.
- 사용 횟수나 생성량으로 무료 범위를 조절한다.
- 사용자가 불편해서 결제하는 것이 아니라, 더 많이 사용하고 싶어서 결제하게 한다.
- 최소한의 무료 사용 기회는 계속 유지한다.

### 초기 무료 사용량 후보

초기 기준은 월 30회 무료 사용을 검토한다.

실제 이용자가 증가하고 API 비용이 높아지면 다음 순서로 조정할 수 있다.

```text
월 30회
→ 월 20회
→ 월 10회
```

가능하면 최종적으로도 월 10회 정도의 무료 사용 기회는 유지하는 방향을 검토한다.

하루 1회 방식보다 월간 사용량 방식이 적합하다.

사용하지 않는 날의 횟수를 잃지 않고, 필요할 때 여러 작업을 몰아서 할 수 있기 때문이다.

### 정책 결정 방법

무료 횟수는 미리 확정하지 않는다.

초기 사용자들의 실제 사용 패턴을 확인한다.

- 한 사용자가 한 달에 몇 회 생성하는가.
- 콘텐츠 한 건당 API 비용이 얼마인가.
- 무료 사용자 중 유료 전환 비율은 얼마인가.
- 월 10회, 20회, 30회 중 어느 구간에서 만족도가 높은가.
- 서버와 AI 비용이 감당 가능한가.

사용자가 실제로 생긴 뒤 데이터를 보고 최종 무료 횟수를 결정한다.

## 7. 유료 서비스 방향

유료 사용자는 단순히 기능 잠금을 해제하는 사람이 아니다.

무료 범위보다 더 많은 콘텐츠를 만들고, 업무 시간을 더 크게 줄이고 싶은 사용자다.

### 유료 정책 후보

- 월간 생성 횟수 확대
- 고속 생성
- 대량 콘텐츠 생성
- 여러 사업장 관리
- 브랜드별 템플릿 저장
- 자동 저장 및 보관함 동기화
- 고품질 AI 모델 사용
- 경쟁 업체 분석
- 예약 생성
- 팀원 또는 직원 계정
- 고객 전용 보고서
- 이미지·오디오·영상 생성 확대

가격은 토큰 비용 자체가 아니라 사용자가 절약하는 시간과 대행 비용을 기준으로 설계한다.

소상공인은 AI 기술 자체보다 다음 가치에 비용을 지불한다.

> 두세 시간 걸리던 콘텐츠 작업을 몇 분 안에 끝낼 수 있는 편리함.

## 8. AI 모델과 API 운영 방향

Gemini 무료 API는 개발과 테스트에 유용하지만, 외부 서비스의 핵심 엔진으로만 사용하기에는 일일 사용량 제한이 문제가 될 수 있다.

특히 한 번의 요청으로 8개 채널 콘텐츠를 생성하더라도 사용자 수가 늘어나면 무료 할당량을 빠르게 소진할 가능성이 있다.

따라서 실서비스는 유료 API와 자동 폴백 구조를 고려한다.

### 운영 구조 예시

1. 1순위: 비용이 저렴한 유료 모델
2. 2순위: 품질 보강 모델
3. 3순위: 장애 발생 시 대체 모델

후보 구조:

```text
DeepSeek
→ Gemini
→ Nemotron 또는 다른 대체 모델
```

### 모델 선택 기준

- 입력 및 출력 토큰 가격
- 한국어 콘텐츠 품질
- 응답 속도
- 긴 결과물의 형식 준수
- JSON 또는 구조화 출력 안정성
- 장애 발생 빈도
- 요청 속도 제한
- API 정책의 지속 가능성

무료 API는 테스트용으로 유지하고, 실서비스는 비용을 지불하더라도 안정적인 구조로 전환하는 것이 바람직하다.

## 9. 업종별 서비스 확장

StoryMaker를 메인 브랜드로 두고 업종별 서비스를 확장한다.

예시:

```text
StoryMaker
├─ 부동산스토리
├─ 식당스토리
├─ 집수리스토리
├─ 헬스장스토리
├─ 쇼츠스토리
└─ 지역사업자스토리
```

각 서비스는 별도의 시스템을 새로 만드는 방식이 아니다.

로그인, 결제, 콘텐츠 생성, 저장, 보관함, 분석 엔진은 공통으로 사용한다.

업종별로 달라지는 부분은 다음과 같다.

- 입력 항목
- 프롬프트
- 콘텐츠 템플릿
- 업종 전문 용어
- 추천 키워드
- 경쟁 업체 분석 기준
- 채널별 결과 형식

한 업종에서 먼저 실제 사용자를 확보하고, 검증된 구조를 다른 업종으로 확장한다.

### 초기 후보 업종

- 부동산 중개업
- 음식점
- 집수리 및 인테리어
- 헬스장
- 학원
- 지역 소상공인
- 쇼츠 제작자

특히 사무실에서 컴퓨터를 자주 사용하고 반복적인 홍보 업무를 하는 업종이 적합하다.

## 10. 경쟁 업체 분석 기능

장기적으로 지역 업체의 공개 정보를 수집해 분석하는 기능을 검토한다.

### 수집 후보

- 구글 지도 및 비즈니스 프로필
- 네이버 플레이스
- 카카오맵
- 네이버 블로그
- 업체 홈페이지
- 유튜브
- 인스타그램
- 당근 비즈프로필

### 공개적으로 확인 가능한 정보

- 업체명
- 검색 노출 순서
- 평점
- 리뷰 수
- 주소
- 카테고리
- 최근 게시물
- 콘텐츠 게시 빈도
- 리뷰 증가 추이
- 홈페이지 및 SNS 운영 여부

브라우저에서 동적으로 표시되는 정보는 Playwright 같은 브라우저 자동화 기술을 활용할 수 있다.

다만 서비스별 이용약관과 공개 정보 범위를 준수해야 한다.

이 기능은 즉시 개발하지 않고, StoryMaker의 기본 콘텐츠 생성과 사용자 경험을 안정화한 뒤 천천히 검토한다.

## 11. 데이터와 개인정보 보호

고객이 생성한 콘텐츠와 파일은 가능한 한 고객이 직접 소유하고 관리할 수 있게 한다.

### 기본 방향

- 생성 결과를 고객 로컬 장치에 저장
- 장기간 보관 가능
- 인터넷 연결 없이 기존 결과 확인 가능
- 서버 저장 부담 감소
- 고객 개인정보와 사업 자료 보호
- 사용자가 원할 때만 서버 동기화

다만 로컬 저장만 사용하면 PC 교체, 고장, 실수로 인한 삭제 시 복구가 어렵다.

따라서 다음과 같은 선택형 구조가 적합하다.

```text
기본: 로컬 저장
선택: 서버 보관함 동기화
선택: 백업 파일 다운로드
```

고객은 자신의 데이터를 직접 보유하고, 서버 보관이 필요한 경우에만 동기화를 선택할 수 있어야 한다.

## 12. 로컬 처리와 서버 구조

StoryMaker는 가능한 작업을 사용자 브라우저나 로컬 컴퓨터에서 처리해 서버 부담을 줄인다.

### 활용 기술

- WebGPU: 브라우저에서 GPU 연산 수행
- WebAssembly: 브라우저에서 고성능 코드 실행
- WebCodecs: 브라우저에서 영상과 오디오 처리
- 로컬 파일 저장
- 선택형 로컬 보조 프로그램

### 서버가 담당할 기능

- 로그인
- 회원 관리
- 결제 및 사용량 관리
- AI API 호출
- 사용자 설정 동기화
- 필요한 데이터 보관
- 폴백 모델 관리

### 사용자 PC가 담당할 수 있는 기능

- 이미지 처리
- 오디오 처리
- 영상 렌더링
- 미리보기
- 파일 변환
- 파일 저장
- 압축 및 다운로드

처음부터 무거운 로컬 프로그램을 필수 설치하게 하지 않는다.

웹앱으로 가능한 기능을 먼저 구현하고, 운영체제 기능이 꼭 필요한 경우에만 선택 설치형 로컬 도우미 프로그램을 검토한다.

## 13. 서버 확장 전략

초기에는 Dell 장비를 활용해 서비스를 운영한다.

현재 고려 순서:

```text
Dell 서버
→ 5800X 서버 활용
→ 실제 사용자 증가
→ 서버 한계 측정
→ 클라우드 이전 또는 확장
```

사용자가 충분히 늘기 전에 클라우드 비용을 먼저 부담하지 않는다.

성능 문제가 실제로 나타날 때 다음 지표를 기준으로 확장한다.

- 동시 사용자 수
- API 호출량
- CPU와 메모리 사용률
- 작업 대기시간
- 파일 저장 용량
- 장애 발생 빈도
- 월간 운영비

사용자 PC에서 처리할 수 있는 작업은 로컬로 보내고, 서버는 꼭 필요한 업무만 맡기는 방향을 유지한다.

## 14. 개발 우선순위

다음 개발에서는 화려한 신규 기능보다 실제 사용자의 손을 덜어주는 기능을 먼저 개선한다.

우선순위:

1. 콘텐츠 생성 결과의 품질과 형식 안정화
2. 복사 버튼과 다운로드 기능 개선
3. 채널별 결과 자동 분류
4. 입력 항목 최소화
5. 한 번의 입력으로 여러 채널 콘텐츠 생성
6. 생성 실패 시 자동 재시도
7. AI 모델 자동 폴백
8. 무료·유료 사용량 관리
9. 회원 관리
10. 결제 관리
11. 로컬 파일 저장 강화
12. 업종별 템플릿 확장
13. 경쟁 업체 분석 기능 검토
14. 사용자 증가 후 서버 확장

## 15. 최종 서비스 철학

StoryMaker는 사용자를 AI 전문가로 만들기 위한 서비스가 아니다.

사용자가 AI를 잘 몰라도 자신의 업무를 빠르게 처리할 수 있게 만드는 서비스다.

최종 서비스 철학은 다음과 같다.

- 기능은 충분히 제공한다.
- 사용자의 시간을 절약한다.
- 반복 작업을 코드로 자동화한다.
- AI는 필요한 부분만 보조한다.
- 결과물은 바로 사용할 수 있게 제공한다.
- 고객 데이터는 고객이 소유한다.
- 무료 사용자도 실제 가치를 경험하게 한다.
- 사용자가 불편해서가 아니라 만족해서 결제하게 한다.

---

## 16. 오늘의 최종 판단

StoryMaker는 대규모 성공만을 목표로 하지 않는다.

개발자 본인이 즐겁게 사용할 수 있고, 실제 생활비와 서버 비용에 보탬이 되는 지속 가능한 서비스가 우선이다.

사용자가 많아지면 확장하고, 많아지지 않더라도 직접 사용하는 유용한 도구로 남을 수 있다.

따라서 조급하게 모든 기능을 완성하기보다 다음 기준으로 천천히 발전시킨다.

```text
내가 실제로 편한가
→ 다른 사용자도 편한가
→ 반복 사용 의사가 있는가
→ 비용을 지불할 가치가 있는가
→ 서버와 API 비용을 감당할 수 있는가
→ 검증된 기능만 다음 업종으로 확장
```

StoryMaker의 성공 기준은 기능의 화려함이 아니라, 사용자가 수작업 방식으로 돌아가기 싫다고 느끼는 편리함이다.

---

## 17. 향후 의사결정 기준

새 기능을 제안하거나 개발할 때는 다음 질문을 먼저 확인한다.

1. 이 기능이 실제 사용자의 입력과 클릭을 줄이는가.
2. 현재 반복되는 업무를 자동화하는가.
3. 결과물이 즉시 사용할 수 있는 형태로 제공되는가.
4. 기존 화면과 작업 흐름을 더 복잡하게 만들지는 않는가.
5. 서버 비용이나 API 비용보다 사용자 절약 시간이 더 큰가.
6. StoryMaker의 핵심 제작 흐름을 안정화한 뒤 추가해도 늦지 않은 기능인가.

위 기준을 통과하지 못하는 기능은 개발 우선순위를 낮춘다.

## 18. 한 문장 방향성

> StoryMaker는 AI를 보여주는 서비스가 아니라, 소상공인의 반복적인 콘텐츠 업무를 줄이고 바로 쓸 수 있는 결과물을 만들어주는 실용적인 업무 자동화 서비스다.
